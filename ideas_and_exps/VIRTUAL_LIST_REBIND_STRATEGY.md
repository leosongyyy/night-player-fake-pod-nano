# 虚拟列表滚动性能：重绑策略之后的下一步（可行性调查）

> **本文性质：调查报告 + 方案清单，尚未落地任何代码改动。**
> **来源**：`DONE_PLANS.md` 第 34 点的尾巴——`IRAM_AUDIT_LVGL9.md` §13.4 第 2 条：
> 「若要继续提速，方向在别处（绘制管线、虚拟列表的重绑策略等），不是继续钉对象。」
> **基线环境**：2026-10-16 之后、LVGL 9.4 + ESP-IDF 6.1 + TTF 字体，
> 构建类型 `debug / cs43131 / ttffont`（`build/cs43131.ttffont.debug`），设备 COM12。
> **已知实测基线**（`IRAM_AUDIT_LVGL9.md` §12/§13）：列表快速滚动 **15 fps**、
> 慢速滚动 **20+ fps**，30 fps 目标未达成；画圈滚动期间 Core0 占用 92~97%。

---

## 0. 一句话结论

**当前重绑策略本身已经接近最优粒度**（每跨一行只重绑 1 行，O(1)），
继续抠"重绑"两个字收益有限；真正的天花板在两件与重绑无关的事上：

1. **LVGL 的滚动在源码里就是"整块失效"**——`lv_obj_scroll_by_raw()` 无条件
   `lv_obj_invalidate(obj)`，于是每帧要重绘**整个列表区（≈180K 像素、≈110 个汉字
   字形）**，而不是"变化的那一行"。
2. **fps 与单帧耗时是连续的反比关系，没有"跳档巧取"的空间**——
   本项目开了 `LV_USE_PERF_MONITOR`，刷新定时器在渲染前**不会**被暂停
   （`lv_refr.c:366` 的 `#if !LV_USE_PERF_MONITOR lv_timer_pause(tmr)`），
   渲染一结束 `lv_timer_time_remaining()` 立刻为 0，`lvgl_port_task` 只 delay 1 ms
   就开下一帧。所以 `fps ≈ 1000 / (单帧渲染 ms + 1~2)`。
   **15 fps ⇒ 单帧 ≈ 65 ms；要 30 fps 就是必须把 65 ms 实打实砍到 32 ms（腰斩）。**
   （⚠ 本节曾一度写成"33 ms 节拍跳档、跨过门槛即翻倍"——那是**错的**，
   已在 §2.1 更正说明原因。）

因此本报告的推荐路线是：**先实测把 65 ms 花在哪里查清**，
再决定投入哪一侧——因为"S1 出局"（见下）之后，剩下的全部手段都只能
"降低单帧成本"，而 65 ms 的构成决定了到底能不能腰斩。

> **已决策（2026-10-16，用户）**：**方案 S1（视口槽位制 + 自管滚动）出局**——
> 前提是触摸滚动只能按整行吸附、失去连续跟手，用户不接受。
> 因此"把整块 dirty 降成一条窄带"这条结构性捷径**已关闭**，
> 剩下的只有"降低单帧绘制/重绑成本"这一条路（§5.1 的 F 系列 + §5.2 的 S2/S3）。

## 1. 现状：一个滚动帧到底做了什么

以歌曲列表页为例（460×392 视口、`PLIST_ITEM_H=56`、可见 7 行、`row_count=9`）。
每一帧（滚动事件驱动）的完整链路：

| # | 步骤 | 源码位置 | 量级 |
|---|---|---|---|
| 1 | `lv_obj_update_layout(list)` | `lv_obj_scroll_by_bounded` (`lv_obj_scroll.c:263`) | 每次 bounded 滚动都全树重算布局；ClickWheel 每帧调用 |
| 2 | `lv_obj_get_scroll_top/bottom()` | `lv_obj_scroll.c:136/294` | 遍历列表所有子对象（1 占位 + 9 行容器） |
| 3 | `lv_obj_move_children_by(list, dx, dy, true)` | `lv_obj_scroll.c:422` | **递归**改写所有后代 `coords`：10 个子对象 + 每个行容器的 2 个 label ≈ 28 个对象 × 4 个坐标 |
| 4 | `LV_EVENT_SCROLL` → `vlist_rebind()` | `virtual_list.c:120` | 两次 O(row_count)=O(9) 扫描；跨 N 行时对每个新进视口的行做 5~9 项工作 |
| 5 | `lv_obj_invalidate(list)` | `lv_obj_scroll.c:425` | **⚠ 把整个列表区标脏（460×392 ≈ 180K 像素）** |
| 6 | 绘制：卡片背景填充 + 7 行 ×（图标 + 文本） | `lv_draw_sw_*` | ≈180K 像素底色 + ≈110 个字形的 A8 mask blend |
| 7 | flush：`lv_draw_sw_rgb565_swap` + `esp_lcd_panel_draw_bitmap` | `lvgl_port.c:94/111` | 每块 460×46，共 10 块；净传输 360 KB |

第 7 步的传输时间可以精确算出来：`AMOLED_QSPI_MAX_PCLK = 40 MHz`（4 线 QSPI）
→ 20 MB/s → 全屏 423 KB ≈ **21 ms**，滚动区 360 KB ≈ **18 ms**。
这笔开销目前被绘制掩盖（双缓冲下两者重叠，取较慢的那个）。

### 1.1 重绑这一步到底重绑了多少

`vlist_rebind()` 的粒度确实是"逐个进出"：滚出视口的行回收、滚入的行重绑，
常驻行**完全不动**。但每次重绑一个行槽要做：

```
lv_obj_clear_flag(HIDDEN)                     // 失效一行区域
lv_obj_set_pos(root, 0, index*item_height)    // 失效新旧两处区域
vlist_bind_row():
  ├─ lv_label_set_text(text  = …)  ← 内容真变了，必须
  ├─ lv_label_set_text(icon, …)    ← ⚠ 内容没变也照做：free + malloc + refr_text
  ├─ lv_obj_set_style_text_color(text, …)  ← ⚠ LVGL 无"相同值"短路，每次都 refresh_style
  └─ lv_obj_set_style_text_color(icon, …)  ← 同上
```

两条 ⚠ 是**已在源码里确认的浪费**（不是估计）：

- `set_text_internal()`（`lv_label.c:987`）**无条件** `lv_free` 旧缓冲 + `lv_malloc`
  新缓冲 + `lv_label_refr_text()`——后者会做一次全文宽度测量
  （`lv_text_get_size_attributes`，逐字符查字形度量），超宽时还会 `lv_anim_start()`
  重建跑马灯动画。文本一个字都没变也照走一遍。
- `lv_obj_set_local_style_prop()`（`lv_obj_style.c`）**没有相同值短路**，
  每次都走 `lv_style_set_prop` + `lv_obj_refresh_style`（→ invalidate）。

对比：**文本 label 已经有这个短路了**（`global_style_marquee_set_text()` 先 `strcmp`，
见 `MARQUEE_STYLE.md`），图标 label 与两处颜色设置没有。

> **小结**：重绑粒度没问题，但"重绑一个行槽"的单价里有两项纯浪费。
> 注意这两项只影响"重绑时"的 CPU，**不影响每帧的绘制量**——而绘制才是大头。

## 2. 四个硬约束（决定了方案空间）

### 2.1 约束一：帧率 ≈ 1000 / 单帧耗时（**更正：不存在"33 ms 跳档"**）

> ⚠ **本节是 2026-10-16 调查过程中的一次自我更正。**
> 初稿曾写"`LV_DEF_REFR_PERIOD=33` 让单帧超过 33 ms 就跳一拍、帧率掉到 15"，
> 并据此提出"跨过 33 ms 门槛即翻倍"的巧取思路。**那是错的**，源码核实如下。

三处源码决定了真实行为：

1. `lv_timer_exec()`（`lv_timer.c:322`）**先写 `timer->last_run = lv_tick_get()`，
   再调用回调**；
2. `lv_display_refr_timer()`（`lv_refr.c:361`）只在**未开性能监视器**时暂停自己：
   ```c
   #if !LV_USE_PERF_MONITOR
       lv_timer_pause(tmr);
   #endif
   ```
   而本项目 `CONFIG_LV_USE_PERF_MONITOR=y` ⇒ **刷新定时器在渲染前不会被暂停**；
3. 于是渲染 65 ms 结束后，`lv_timer_time_remaining()` 判据 `elp(65) >= period(33)`
   已经成立、返回 0，`lv_timer_handler()` 返回 0，`lvgl_port_task` 把它 clamp 到
   `EXAMPLE_LVGL_TASK_MIN_DELAY_MS = 1` → **1 ms 后立刻开始下一帧**。

**结论**：`fps ≈ 1000 / (单帧渲染 ms + 1~2)`，是连续的反比关系。

| 单帧渲染 | 实际 fps |
|---|---|
| 32 ms | 30（此时 33 ms 节拍才成为上限） |
| 48 ms | ~20（对应实测"慢速滚动 20+"） |
| **65 ms** | **~15（对应实测"快速滚动 15"）** |

`LV_DEF_REFR_PERIOD=33` 的真实作用**只有一个**：渲染快于 33 ms 时把上限钉在 30 fps，
**它不是当前的限速原因**。

**对方案的三条影响**：
- ❌ 不存在"跨过某个门槛就翻倍"的巧取空间；
- ✅ 收益是线性的、可外推的：省 X ms → `fps = 1000/(65−X)`。
  省 15 ms → 18 fps；省 25 ms → 25 fps；**必须省掉 33 ms 才到 30 fps**；
- ⚠ **验收口径必须从 fps 改成"单帧毫秒数"**，否则 ±1 帧的噪声会掩盖真实进展；
  同时意味着**单项小优化大概率看不到明显效果，必须凑够量**。

### 2.2 约束二：滚动 = 整块失效（LVGL 源码级行为）

```c
/* lv_obj_scroll.c:413 */
lv_result_t lv_obj_scroll_by_raw(lv_obj_t * obj, int32_t x, int32_t y)
{
    obj->spec_attr->scroll.y += y;
    lv_obj_move_children_by(obj, x, y, true);
    lv_result_t res = lv_obj_send_event(obj, LV_EVENT_SCROLL, NULL);
    if(res != LV_RESULT_OK) return res;
    lv_obj_invalidate(obj);        /* ← 无条件整块 */
    return LV_RESULT_OK;
}
```

这是本次调查**最关键的一条**：它决定了

- 无论重绑多精细、无论行槽是不是"锚定在内容坐标原地不动"，
  **只要走 LVGL 原生滚动，每帧就一定要重绘整个列表区**；
- 所以"把 dirty 区域缩小到变化行"这件事，**在不改 LVGL 的前提下只有一个办法**：
  **不用 LVGL 的滚动**（见 §5.2 方案 S1）。

同时它也解释了为什么 `IRAM_AUDIT_LVGL9.md` 里"对象放内部 RAM"收益那么大：
整块重绘意味着每帧要**反复访问**这批对象/样式/字形的数据结构，
而工作集（≈88 KB）远超 S3 的 32 KB 数据 cache——这是典型的 cache 抖动问题，
不是"画得慢"，而是"取数据慢"。

### 2.3 约束三：QSPI 40 MHz（当前不是瓶颈，但会变成瓶颈）

传输 18 ms/帧目前被 33~66 ms 的绘制掩盖。但一旦绘制被压到 20 ms 以下，
**传输就会顶上来成为新天花板（≈18 ms → 上限 ~55 fps@16ms 节拍）**。
`display.h` 里写着「80M 也是可行的，但杜邦线不行」——成品机是 FPC 排线，
真机上 80 MHz 是否稳需要单独验证（不属于本次调查范围，但要记在账上）。

### 2.4 关键线索：65 ms 的构成（为什么快速比慢速慢 15 ms）

实测：快速滚动 15 fps（≈65 ms）、慢速滚动 20+ fps（≈48 ms）。
**两者每帧的重绘量应该是一样的**（都走整块 invalidate），所以这 15 ms 的差额
只能来自"每帧重绑了多少行"，或者来自"慢速时并非每帧都在滚"。

ClickWheel 的行对齐步进让"一帧跨几行"变成可计算的
（`CW_MAX_STEP_PX=800 / item_h 56` ⇒ 单帧最多 14 行；慢速时通常 1~2 行）：

| | 解释 | 推论 |
|---|---|---|
| **甲** | 差额全归**重绑单价** | 一帧多绑 ~13 行 ⇒ **单行重绑 ≈ 1.1 ms（≈264K 周期）**。一行只做 `set_pos` + `set_text` + 2 次颜色设置，正常不可能这么贵；唯一能解释的是 `lv_label_refr_text()` 里 `lv_text_get_size_attributes()` 的逐字度量，以及字形缓存 miss 时 FreeType 的光栅化。⇒ **H1 升为第一嫌疑** |
| **乙** | 慢速时存在大量**空帧** | indev 位移不足阈值时不产生 SCROLL 事件 ⇒ `disp_refr->inv_p == 0` ⇒ 该拍直接 `goto refr_finish`（`lv_refr.c:415`，几乎不耗时）。那么"20+ fps"里混了大量空帧，**真实滚动帧率可能同样是 ~15 fps** |

两种情况都说得通，**必须实测区分**——这也是 §4 的 E1/E2 绕不过去的原因。

⚠ 但无论甲乙哪个成立，有一条**战略结论已经确定**：

> **`IRAM_AUDIT_LVGL9.md` 实测"慢速滚动 20+"意味着单帧底座至少 48 ms。
> 即使把重绑成本压到 0，也只能到 20 fps。**
> 要触碰 30 fps，必须动"每帧整块重绘"这 48 ms 的底座
> （对象/样式访问 + 字形 blend + 底色填充 + 绘制管线），
> 而这一侧目前**没有任何已验证的抓手**。

这正是本次调查得出"先测再动"的原因：65 ms 里"可省的浪费"（重复光栅化、重绑冗余）
与"物理必需"（真的要把 10 行汉字画出来）各占多少，决定了这件事到底能不能做。

### 2.5 用户体感观测：帧率忽高忽低（单帧时间剧烈波动）

> 2026-10-16 用户实测反馈：「看起来是帧率忽高忽低，单帧时间有剧烈波动导致实际体验较卡。
> 能忍，但希望改善。」

这条观测本身是重要线索——**波动**比"均值低"更容易被眼睛读成卡顿，
而且它排除了"单帧耗时稳定在 65 ms"这种简单图景（稳定的 15 fps 观感是"匀速偏慢"，
不是"一顿一顿"）。候选来源：

| 候选 | 机制 | 判别方法 |
|---|---|---|
| 字形缓存 miss 的随机性 | 新汉字 miss（含光栅化）与命中帧的耗时差一个量级 | 大幅加大字形缓存后波动是否消失（F2） |
| 跑马灯动画重启/相位 | `lv_label_refr_text()` 在文本变化时重建滚动动画；`global_style` 守护定时器每 200 ms 兜底 | 关掉跑马灯看波动是否变小 |
| ClickWheel 跨行尖峰 | 单帧最多跨 14 行（`CW_MAX_STEP_PX=800 / item_h`），重绑量本身差 14 倍 | 固定速度画圈对比 |
| **Core1 争抢 PSRAM 带宽** | 播放中 MP3 解码持续读写 PSRAM，与 Core0 的对象/字形访问争带宽；封面解码是突发大流量 | **对比"暂停播放"与"播放中"滚动的帧率** |
| LVGL 其他 timer 的叠加 | `lv_timer_handler` 同时驱动跑马灯守护、`player_ticker` 等多个 timer | E1 直方图的多峰形态 |

⚠ **最后第二条（PSRAM 带宽竞争）尤其值得先查**：它意味着"列表滚动性能"不是纯 UI 问题，
而是与播放状态耦合的（也能解释为什么不同场景主观感受差异大）。
若成立，则 §4 的 E1 测量必须**固定在同一个播放状态下**做，否则数据不可比
——这也可能是"快速 15 / 慢速 20+"这组历史数据本身就不稳的原因之一。

### 2.6 约束四（用户提出）：资源占用必须与列表长度无关（O(1)）

> 2026-10-16 用户：「长条方案应该严正否决，**因为存在单条 1000+ 的列表，长条必然会爆炸**。」

这是本项目列表规模带来的硬性约束：大曲库与根目录会出现**单条 1000+ 项**的列表，
因此**任何随 `item_count` 增长的分配、缓存或状态表都必须排除**。

**当前实现满足这条**（已逐行核对 `virtual_list.c`）：

| 项 | 规模 | 与 item_count 的关系 |
|---|---|---|
| `st->rows` / `st->row_indices` | `row_count` = 可见数 + 2 = **9** | **无关**（只由视口高度与行高决定，`virtual_list.c:304/307/308`） |
| `st->data` | 指向 `pldata` 的 mmap | **无关**（不复制数据，只算指针偏移） |
| 占位对象高度 `content_h` | 一个 `lv_coord_t` **标量** | 无关。1085 项 × 56 px ≈ 60.8K px，远在 LVGL 9 的 int32 之内（v8 时代这正是必须开 `LV_USE_LARGE_COORD` 的原因） |
| 滚动条 / ClickWheel 圈数模型 | 常量状态 | **无关** |

⇒ **这是本项目虚拟列表最有价值的一条既有设计**，任何改造（包括 S4）都必须原样保持。
它同时也直接否掉了"长条/跨帧复用"那一类方案（见 §5.3 第一条）。

## 3. 瓶颈候选（H1~H5）与各自的可验证预言

本报告**不假设**瓶颈归属，而是把候选列成可证伪的预言，用 §4 的实验一次问清。

| 编号 | 假设 | 支持它的现有证据 | 若成立，预言 |
|---|---|---|---|
| **H1** | **FreeType 字形光栅化 cache miss**：1024 条字形缓存被滚动刷爆，每帧要重新光栅化几十个汉字 | §2.4 的"甲"解释：快速滚动比慢速慢 15 ms，而两者重绘量相同；反推"单行重绑 ≈1.1 ms"只能用逐字度量/光栅化解释；`LV_FREETYPE_CACHE_FT_GLYPH_CNT=1024` 对数千汉字明显偏小 | 缓存加到 4096 应显著改善**快速**滚动，而对静止画面与慢速滚动几乎无影响 |
| **H2** | **字形 mask blend（纯像素工作量）** | 每帧 ≈110 字形 × ≈576 px ≈ 63K 像素的 A8 blend，外加 180K 像素底色填充 | 文本变短（少字形）帧率应明显上升；加大字形缓存无效 |
| **H3** | **对象/样式访问（cache 抖动）** | 审计实测"对象放内部 RAM 21 vs PSRAM 11 fps"，是所有杠杆里最大的 | 继续减少每帧访问的对象数/样式属性数应有可观收益 |
| **H4** | **重绑本身** | 每跨一行 5~9 项操作，且含 §1.1 两项纯浪费 | **跳过重绑**（画面会错乱）后帧率应大幅上升；若无变化则重绑不是瓶颈 |
| **H5** | **绘制管线固定开销**（draw task、layer、逐对象事件派发） | LVGL 9 管线比 8.4 深得多（栈从 6KB 涨到 20KB 是旁证） | 减少行槽对象数（去掉行容器）应有收益，且与文本长度无关 |

## 4. 实验设计（建议一次烧录问清 H1/H2/H4）

目标：**测出"单帧渲染毫秒数"以及它在各候选之间的分配**，而不是只测 fps。

**E1（最直接，先做这个）——单帧耗时直方图**
在 `lvgl_port_task()` 里对 `lv_timer_handler()` 的前后打 `esp_timer_get_time()`，
只统计耗时 > 1 ms 的调用（即真正干了刷新的那些帧），每 2 s 打印
`帧数 / 平均 ms / P50 / P90 / 最大 ms`。
> 这一步就能回答"单帧离 30 fps 所需的 32 ms 还差多少"，并给后续所有改动一个统一标尺。
> 现有 `performance_monitor` 只有 CPU% 与内存，没有这个口径。

**E2——三段对照，分离"重绑"与"绘制"**（同一个固件内用 `lv_timer` 自动滚动，
无需人工滑屏）：第 1 段正常重绑 → 第 2 段 `vlist_rebind()` 直接 return（画面错乱，仅测量用）
→ 第 3 段完全静止。比较三段平均单帧毫秒数：
- 段 3 ≈ 静止基线（跑马灯仍在跑）
- 段 1 − 段 2 = **重绑的真实成本**
- 段 2 − 段 3 = **纯绘制 + 滚动的成本**

**E3——字形缓存敏感性**：`CONFIG_LV_FREETYPE_CACHE_FT_GLYPH_CNT` 1024 → 4096
（只吃 PSRAM，6.4 MB 可用），重跑 E1/E2。验证 H1。

**E4（可选）——文本长度敏感性**：拿一个"文件名很短"的目录与"文件名很长"的目录对比，
验证 H2（长文本 → 更多字形 → 更慢）。

> ⚠ 以上都是**临时测量代码**，按项目约定测完必须清理（或收进 Kconfig 开发者选项）。
> E1 建议长期保留在开发者选项下——它是本次唯一"以后每次调优都用得上"的尺子。

#### 5.2.1 方案 S4：自己接管列表绘制（用户提出，2026-10-16 修订）

> **来源与修订**：
> ① 用户最初提出——「既然列表都要重绘，能否把整个列表用 Canvas 之类一次性绘制到画面上？
> NightPlayer 的前身 FantasticMusicPlayer 也是这么干的，绘图表面可以放进 PSRAM 里」；
> ② **同日用户修订**——「**不是**一次性绘制整个列表，而是**只提供一个和视口大小一样的
> 缓冲区，按照位置只绘制需要的项目**；列表的**坐标和惯性计算之类的东西可以放在 IRAM 里**，
> 同时**缓存小图标**。」
> **本条是对修订后方案的可行性评估，尚未实施。**

##### 修订带来的两个根本变化

1. **不再需要"内容长条 surface"**：不需要跨帧复用、不需要基准跳跃管理，
   只要一块**视口大小**的缓冲，按当前滚动位置把可见行画进去即可。
   实现复杂度大幅下降，内存从 ≈618 KB 降到 ≈360 KB（甚至降为 0，见下）。
   ⚠ **长条方案已被严正否决**（理由见 §5.3 第一条与 §2.6 约束四）：
   "视口大小"是它的唯一合法形态，**任何形式的跨帧内容缓存都不要做**。
2. **热状态与图标改为显式放进内部 RAM**：坐标/惯性/行索引等运行时数据直接由我们分配
   （`heap_caps_malloc(MALLOC_CAP_INTERNAL)`），图标预渲染成小位图缓存。
   ⇒ 这也**天然取代了"路径B"**：S4 下 LVGL 对象只剩 1 个，
   `IRAM_AUDIT_LVGL9.md` §13 那套"把 19 个行槽对象钉进内部 RAM"的窗口机制不再需要。

##### 关键实现判断：缓冲放哪，决定有没有"额外搬运"（最容易踩的坑）

- 若"视口缓冲"是**另一块内存**（PSRAM，460×392×2 = 360 KB），那么每帧除了绘制内容，
  还要把整块**搬运一次**到 LVGL 的 DMA 绘制缓冲（partial 模式 460×46 一块 × 10 块）。
  这笔搬运 = 360 KB 从 PSRAM 读 ⇒ **额外 7~9 ms/帧，是现在没有的开销**，
  会抵消掉相当一部分省下来的对象开销。
- 若把"视口缓冲"实现为 **LVGL 的自定义绘制回调（`LV_EVENT_DRAW_MAIN`）**，
  直接画进 LVGL 当前的绘制缓冲，就**没有任何额外搬运**，同时照样绕开对象树。
  **⇒ 推荐这条路**——"视口大小"在实现上就等价于"这次 draw 回调覆盖的区域"，
  它天然就是 LVGL 按缓冲高度切出来的块，不需要我们自己管。

**抓手（已确认全部在 LVGL 9.4 公开头里）**：

```c
lv_obj_add_event_cb(list, vlist_draw_cb, LV_EVENT_DRAW_MAIN, NULL);

static void vlist_draw_cb(lv_event_t *e)
{
    lv_layer_t *layer = lv_event_get_layer(e);          /* lv_obj_event.h */
    /* 1) 一次 lv_draw_rect 铺满列表区底色（顺带省掉卡片背景那一层） */
    /* 2) 按 scroll_y 算可见行，逐行 lv_draw_label() 直接把文本写进去 */
    /* 3) 图标用预渲染位图 + lv_draw_image()（不再走字形路径） */
}
```

- `lv_draw_label(lv_layer_t *, const lv_draw_label_dsc_t *, const lv_area_t *)` 是公开 API；
- `lv_draw_image()` 同理（给图标位图用）；
- **样式链完全不用解析**（`dsc` 里的 font/color/size 由我们直接填）——这正是砍 H3/H5 的关键；
- 行槽仍是 `SCROLLABLE` 的对象，所以**滚动手感、惯性、原生滚动条全部保留**
  （不需要 S1 那套自管滚动，也就不触碰已被否决的整行吸附）。

##### 它砍掉什么、没砍掉什么

| 每帧工作 | 现状 | S4（修订版） |
|---|---|---|
| LVGL 对象（遍历 / 事件派发 / 样式解析） | **19 个** | **1 个**（列表容器自己）→ **砍掉 H3、H5** |
| draw task 数量 | ≈19+ | **9**（每行一个 `lv_draw_label`） |
| 字形 mask blend | ≈126 个汉字 | **≈126 个汉字（没省）** ← H2 照旧 |
| 重复光栅化 | 每帧都在赌缓存命中 | **没省** ← H1 照旧 |
| 额外内存搬运 | — | **0**（画进 LVGL 绘制缓冲） |

> ⚠ **这是修订版与"长条 surface"最大的取舍点**：
> 修订版砍的是**对象 / 样式 / 管线**（H3/H5），**不是**字形渲染（H1/H2）——
> "每帧按位置重画可见行"意味着每帧仍要把那 126 个汉字画一遍。
> 如果 E1/E2 测出底座主要是字形渲染，修订版收益有限，需要配 F2（加大字形缓存）
> 或 S3（SIMD blend）；若要连 H1/H2 一起省，就得回到"跨帧复用"（长条），
> 或接受每帧重画。

##### 用户要求的两项优化的具体做法

1. **坐标 / 惯性状态放 IRAM**：行索引数组、行 y 坐标、`scroll_y`/速度、文本指针数组等，
   直接用 `heap_caps_malloc(MALLOC_CAP_INTERNAL)` 分配（不再依赖 `lvgl_mem` 窗口）。
   ⚠ 这些数据**必须支持小数相位**（滚动是连续的），所以存 `int32_t` 坐标，
   行槽的屏幕 y = `index * item_h − scroll_y`，**不是整行吸附**。
2. **小图标缓存**：图标当前是 `LV_SYMBOL_*` 字形（`lv_font_montserrat_20`），
   每帧走 `lv_font_get_glyph_bitmap` + blend。改为**每种图标预渲染一张小位图**
   （本项目只用到 4 种：`LV_SYMBOL_AUDIO` / `_DIRECTORY` / `_LIST` / `_SD_CARD`），
   20×20×2 B × 4 ≈ **3.2 KB，可整体放进内部 RAM**，绘制时直接 `lv_draw_image` blit。
   ⇒ 收益本身不大（9 个图标仅 ≈3.6K px），但能去掉一条每帧的字形路径，顺手可做。

##### 剩余风险与工作量

1. **跑马灯要自己实现**（最大工作量）：不能再靠 `lv_label` 的动画，要在 draw 回调里
   按自己的 offset 画那一行。代价是每帧多画 1~2 行的字形——可接受，
   但 `global_style` 的"起始延迟 / 3 轮 / 轮间停顿"节奏要自己复刻。
2. **文本度量**：跑马灯需要知道文本宽度来决定是否滚动，自己绘制时要自己调
   `lv_text_get_size_attributes()`（或自己缓存宽度）。
   ⚠ 这一项**仍然会走 FreeType 度量**，是 H1 的残余。
3. **切歌高亮 / 点击命中**：高亮由 draw 回调按当前曲目判断（天然解决，
   不再需要 `virtual_list_refresh()` 重绑全部行）；点击命中改为按 y 坐标算行号。
4. **按下反馈**：黄色背景可在 draw 回调里按 `pressed_index` 画，或用一个独立覆盖矩形。
5. **PSRAM 带宽竞争**：播放时 Core1 的 MP3 解码在读写 PSRAM，与 Core0 争带宽。
   修订版没有额外搬运，所以这一项影响比长条版小得多，但仍会影响字形缓存访问。

##### 结论

**修订版是目前风险最低、兼容性最好的自绘方案**：不动手感、不动 LVGL 的滚动与滚动条、
没有额外内存搬运，代价是**每帧仍要画 126 个汉字**（H1/H2 照旧）。
它本质上是一个"**把 H3/H5 从方程里消掉**"的干净实验——
若 E1/E2 显示底座主要是对象/样式开销，它能拿到大头；
若底座是字形渲染，它拿不到多少，那就得回到长条复用（原 S4）或上 SIMD。

⚠ **实施前仍建议先做第 0 阶段测量**（§4 的 E1/E2），否则无法判断它值不值得写。

### 5.3 明确不建议的方向（避免重复劳动）

- **⛔ 长条 / 跨帧复用的离屏内容缓存（报告初稿的 S4-a）——用户 2026-10-16 严正否决**。
  两条理由：
  1. **产品约束（用户提出）**：本项目存在**单条 1000+ 项**的列表（大曲库、根目录）。
     "长条"要真正兑现"滚动时不重画字形"的价值，就得缓存**足以覆盖滚动范围**的内容
     ——那就必然按 `item_count` 分配，1000+ 行必然爆炸。**违反 §2.6 的约束四。**
  2. **技术印证**：若把它缩成**固定窗口**（初稿设想的是 12 行 / ≈618 KB PSRAM），
     它其实就**退化**了——ClickWheel 行对齐步进下单帧最多跨 **14 行**
     （`CW_MAX_STEP_PX=800 / item_h 56`），会直接冲垮 12 行窗口，
     触发"基准跳跃 + 整块重画"，于是又回到"每帧重画大部分行"，
     与"视口重绘"（修订版 S4）没有实质差别，却白背一套状态机。
  ⇒ **结论：长条在本项目的列表规模上没有存在价值，以后不要再评估。**
- **继续加大对象钉住窗口**：`IRAM_AUDIT_LVGL9.md` §13.2 已证明 83 KB 之后收益归零，
  且会把 DMA 最大连续块压到 208 B（低于 SD 读一次所需的 512 B）。
- **关闭 `LV_ATTRIBUTE_FAST_MEM_USE_IRAM`**：审计已实测只有 ±1 帧，却要牺牲 IRAM。
- **把 FreeType 字形位图整体钉进内部 RAM**：1024 条 × ≈576 B ≈ 590 KB，装不下
  （内部 RAM 稳态仅 38.8 KB）。
- **缩小绘制缓冲**：那是拿帧率换内存，当前内存并不缺。

## 6. 可行性结论

| 问题 | 结论 |
|---|---|
| 重绑策略本身还有多大空间？ | **粒度上没空间**（已是 O(1)/行），只剩 F4 这类单价冗余。但 §2.4 的"甲"解释提示**重绑单价可能高达 1.1 ms/行**——若成立它就不是小头，值得优先测。 |
| 真正的天花板在哪？ | **LVGL 滚动 = 整块失效**（§2.2）。每帧必须重画整个列表区，而且**慢速滚动也要付这笔底座**（§2.4）。 |
| 有没有"跨门槛就翻倍"的巧取？ | **没有**（§2.1 更正）。fps 与单帧耗时成反比，30 fps 就是要把 65 ms 砍到 32 ms。 |
| 不改交互模型能到 30 fps 吗？ | **未知，且不乐观**。慢速滚动实测已经 48 ms，即重绑成本降到 0 也只有 20 fps；必须同时把"整块重绘底座"砍掉一半。而 S1 已出局，剩下 F2/F5/S2/S3，其中 S2/S3 选哪个完全取决于底座的性质。 |
| 现在还缺什么信息？ | **65 ms 的构成**：其中"可省的浪费"（重复光栅化、重绑冗余）与"物理必需"（真要把 10 行汉字画出来）各占多少。这是决定"这件事能不能做"的唯一输入（§4 的 E1/E2）。 |

## 7. 建议路线（分阶段，先便宜后昂贵）

1. **第 0 阶段（必须先做，但目前被推迟）**：E1 单帧耗时直方图 + E2 三段对照
   （正常重绑 / 跳过重绑 / 静止）。**1 次烧录、不改行为。**
   产出三样东西：单帧毫秒数、重绑占比、"空帧率"（用来分辨 §2.4 的甲/乙）。
   > 用户当前选择"暂不动固件"⇒ 这一步推迟。但它是**所有后续判断的前提**：
   > 在它之前不建议动任何一行优化代码，否则既无法验收收益、也无法归因。

2. **第 1 阶段（便宜、几乎无风险、不改架构）**：F2（字形缓存 1024→4096）+ F4（重绑去冗余）。
   用 E1 的同一把尺子验收：
   - 单帧明显下降 ⇒ H1/H4 成立，进第 2 阶段；
   - 单帧几乎不动 ⇒ **48 ms 底座是"物理必需"的绘制**，此时唯一出路只剩 S3
     （或接受现状），**要果断停手，不要继续零敲碎打**。

3. **第 2 阶段（按 E1/E2 的归因二选一）**：
   - 底座是**对象树/样式解析/绘制管线** ⇒ F5（去行容器，3 obj/行 → 2 obj）+ S2（行位图缓存）；
   - 底座是**字形 blend 的像素工作量** ⇒ S3（Xtensa LX7 SIMD 重写 RGB565 mask blend）。
     ⚠ 当前是 `LV_DRAW_SW_ASM_NONE`，需要走 `LV_DRAW_SW_ASM_CUSTOM` 自行提供内核。

4. **第 3 阶段（自绘方案，长期候选）**：**S4 自己接管列表绘制**（§5.2.1，用户提出并修订）。
   推荐形式是**自定义绘制回调**（`LV_EVENT_DRAW_MAIN` + `lv_draw_label`）直接画进
   LVGL 的绘制缓冲——零额外搬运、绕开对象树、完全保留原生滚动手感。
   它砍的是 **H3/H5**（对象/样式/管线，19 个对象 → 1 个），
   **不砍 H1/H2**（每帧仍要画 ≈126 个汉字）。
   ⚠ 因此它值不值得写，完全取决于第 0 阶段的归因：
   底座若是对象/样式开销 → 它能拿大头；底座若是字形渲染 → 收益有限。

5. **第 4 阶段**：F1（节拍 33→16）——**只在单帧已 <33 ms 之后做**，否则零收益。
   （S1 已出局，不再列入路线。）
