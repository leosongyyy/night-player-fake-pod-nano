# 坏曲播放导致堆破坏崩溃的定位与修复（首帧门禁 + 自动跳过）

> 关联提交/改动：`main/core/hardware/audio/mp3_player.c`、`main/core/player/player_controller.c`、
> `sdkconfig.defaults.debug`、`sdkconfig.defaults.releasecandidate`（heap poisoning 常驻）。
> 本文档记录前因后果，供后续遇到"某个文件一播就死机/整机重启"类问题参考。

---

## 1. 背景与现象

用户某张 SD 卡上出现一个"坏文件"，表现为：

- 播放器播放该曲目后**死机重启**；最早阶段**无日志且开机屏幕不亮**（连日志都来不及出）；
- 怀疑封面（`.ecov`/`.npd` 侧车文件）有问题 → 删除后开始有日志，但问题仍在；
- 用特殊手段绕过这首歌后其它歌全部正常，**只有点它必卡死**；
- 在电脑上读该文件：打不开，十六进制显示**大段 0 且混杂着其它文件的文件名**
  ——典型文件系统损坏产物（该卡已多次出现 FS 损坏）。

日志快照（第二阶段）：

```
I (1101) mp3_player: skip ID3v2 tag (360661 bytes)   ← 假 ID3v2，声明 36 万字节标签
...
Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
PC: 0x420263b3 ... EXCVADDR: 0xa5a5a5c5 ...
Backtrace: ... lv_label_refr_text / lv_obj_refresh_style / cover_jpeg_decode ...
--- Warning: Checksum mismatch between flashed and built applications.
```

## 2. 日志分析要点（踩坑）

1. **`Checksum mismatch` 意味着串口工具是用"与设备不符的 ELF"在解符号**——崩溃栈里的
   函数名/行号可能张冠李戴（如把中间帧解成 `esp_libc_include_syscalls_impl`、
   `mem_report_stack_hwm` 这类不可能在链上的函数）。**先别信，先让设备跑的固件与
   手头 ELF 一致再抓一次**。
2. `EXCVADDR = 0xa5a5a5c5`：`0xa5a5a5a5` 是 **FreeRTOS 任务栈填充字节**
   （`tskSTACK_FILL_BYTE = 0xa5`，`tasks.c`）。本项目 heap poisoning 是关的，
   释放后的堆块内容不清理，被复用的内存会保留旧内容（包括任务栈的 0xA5）。
3. 本项目把 `CONFIG_HEAP_POISONING_DISABLED` 设为默认（未在任何 defaults 里显式写，
   属 IDF/继承默认），导致**堆越界写静默吞掉**。这也是本文档第 5 节把它常驻
   debug/releasecandidate 的原因。

## 3. 复现与定位过程（COM12 实测）

用**与源码匹配的 releasecandidate 固件**现场复现（临时在 `player_controller_init`
强制开机播放坏曲，验证后已删除该调试段），得到干净调用栈：

```
Core 0 LoadProhibited, EXCVADDR = 0xa5a5a5bd
_lv_obj_get_layer_type (lv_obj_draw.c:392)      ← 读 obj->spec_attr（=0xa5a5a5a5 垃圾）
 ← lv_obj_transform_point / lv_obj_invalidate / lv_obj_refresh_ext_draw_size
 ← lv_obj_refresh_style ← lv_obj_set_style_pad_left (lv_obj_style_gen.c:160)
 ← virtual_list_create (virtual_list.c:281)     ← 播放列表页创建 cell 时
 ← playlist_page_show_dir ← boot 正常进 UI
```

对照实验：

| 实验 | 结果 |
|---|---|
| 强制播放坏曲 #430（同目录） | 100% 崩溃（UI 建播放列表页时） |
| 强制播放同目录好曲 #431 | 不崩，正常播放 |
| 开启 FreeRTOS 栈溢出金丝雀 | 无任何任务栈溢出报告（排除栈溢出） |
| 开启 comprehensive 堆毒化 | 同样崩溃，但崩溃点前移到 `lv_label_create` 构造器内 `get_prop_core`，垃圾仍是 0xA5 |

**结论**：与解码器/文件内容相关，而非列表渲染、栈溢出或 UI 自身。综合证据指向：

> **坏文件（假 ID3v2 头 + 大段 0 + 其它文件字节）进入 Helix 解码器后，在解出任何
> 有效音频帧之前就破坏了堆内存**；随后 Core0 的 LVGL 新建对象/刷新样式时读到被
> 0xA5（已释放并作为新任务栈填充过的堆块）覆盖的悬垂对象 → LoadProhibited。

注意两个反直觉点：
- 破坏发生在 Core1 的解码任务里，崩溃却出现在 Core0 的 UI 上（堆是全局共享的，
  谁先踩到坏块谁崩）。
- 崩溃时**从未打印过 `mp3: …Hz`**（即没有成功解出任何一帧），说明坏数据在
  "找同步字/解坏帧"阶段就已造成破坏——修复必须**阻止垃圾数据进入解码器**，
  而不是等解码器出错再兜底。

## 4. 修复方案

### 4.1 核心：首帧有效性门禁（`mp3_player.c`）

在把数据交给 `MP3InitDecoder`/解码循环之前，先读音频区开头 16KB 做结构性验证：

- `mp3_frame_header_len()`：校验单帧头是否结构合法（同步字 `0xFF Ex`、非保留版本、
  Layer III、码率/采样率索引合法），并按版本算帧长；
- `mp3_find_valid_frame_start()`：要求**连续两个合法帧**（第二帧必须落在第一帧
  计算出的帧长末尾）才放行。

真实 MP3 在 ID3 之后必然很快出现连续合法帧；而"假 ID3 + 0 填充 + 随机文件字节"
几乎不可能凑出两个连续合法帧（随机字节偶发一个合法帧头都有 ~1/2^16 概率，两帧
连续则概率可忽略）→ 门禁不过 → 视为坏曲，走"自然播完"收尾自动跳下一首，
**垃圾数据从头到尾没进过 Helix**。

踩坑：MPEG 版本表索引与直觉相反——`samplerateTab/bitrateTab` 的约定是
`ver=0 为 MPEG1、1 为 MPEG2、2 为 MPEG2.5`（与 `mp3_read_xing_duration` 一致）。
初版把 MPEG1 帧长误用 72 样本（MPEG2/2.5 公式），导致**所有 320kbps/44.1k 正常歌
也被误杀**（现象：每首歌都打 `no valid mp3 frame at start`）。修复：MPEG1(ver=0)
帧长 = 144×码率/采样率，MPEG2/2.5 = 72×码率/采样率。门禁通过后 `data_offset`
前移到首帧位置，保证时长估算/seek 与解码起点一致。

### 4.2 其它播放层防御（`mp3_player.c`）

- **ID3v2 跳过量钳制到文件实际大小**：损坏文件常见"头声明超大标签"，
  `fseek` 越过 EOF 不报错，会让后续 `data_size = ftell(END) - data_offset`
  下溢成巨大值（seek 映射/CBR 估算全部错乱）。
- `mp3_read_xing_duration` 的偏移同样钳制。
- 标签后没有任何音频数据 → 提前收尾（自动跳下一首），不做空数据解码。
- 解码循环 `MAINDATA_UNDERFLOW` 若输入完全不被消耗（bytes_left 不变）→ 按坏帧
  跳同步字，防止假同步字导致的无限空转。

### 4.3 控制器层自动跳过（`player_controller.c`）

- 自然播完但**总时长 0**（解不出任何有效帧）→ 视为坏曲自动切下一曲；
  正常文件在首帧解出后一定会估算出时长，不会误判。
- **连续 16 首坏曲上限**：达到后停止自动续播并记录"关机前未在播放"，
  防止整目录/整卡损坏时无限空转（尤其单曲目录里只有坏歌时会原地重播风暴，
  还会高频触发 UI 切歌刷新）。
- `player_controller_init` 清空计数。

### 4.4 构建配置：堆毒化常驻 debug / releasecandidate

`CONFIG_HEAP_POISONING_COMPREHENSIVE=y` 加入 `sdkconfig.defaults.debug` 与
`sdkconfig.defaults.releasecandidate`（用户要求保留）。作用：越界写在释放时立即
报 `CORRUPT HEAP` 并打印写入者调用栈，避免再出现"静默破坏、几毫秒后才在
毫不相干的 UI 里炸"的难查现场。性能有少量开销，**release 版不启用**。

## 5. 验证结果（COM12，releasecandidate）

| 场景 | 结果 |
|---|---|
| 强制播放坏曲 #430 | `no valid mp3 frame at start … damaged, skip` → 自动跳下一首，无崩溃 |
| 同目录好曲 #431 | 门禁通过，正常解码播放（44100 Hz / 78 s） |
| 门禁修复前 | 所有 320kbps 歌被误杀（版本表索引 bug，见 4.1 踩坑） |
| 正式固件（删调试段） | 正常恢复 NVS 现场（shuffle 恢复好曲），UI 完整创建，无崩溃 |

## 6. 行为变化与注意事项

1. **点坏曲的体验**：瞬间自动跳到下一首（串口一条 `W mp3_player: no valid mp3
   frame at start … damaged, skip` + 一条 `player_ctrl: bad track … auto skip`）。
2. 门禁的边界情况：若某文件音频区开头 16KB 内没有"连续两个合法帧"（极罕见，
   如 ID3 后还有大段非音频标签字节、自由码率文件），会被当坏曲跳过并打 W 日志。
   遇到再说，可放宽为允许第二帧在小窗口内偏移。
3. 门禁本身是对"损坏文件"的**免疫层**，不是对文件系统损坏的修复：该卡已多次
   FS 损坏，建议备份后格式化 + 校验（chkdsk 等）。
4. 堆毒化仅 debug/releasecandidate 生效；用 release 复现同类问题时先开毒化再复现。

## 7. 可复用排查套路（写给下次）

遇到"特定文件一播就死机"：

1. 先确认**设备固件与本地 ELF 一致**再抓崩溃（看 `ELF file SHA256` 是否匹配），
   否则栈符号不可信；
2. 看崩溃值是否 `0xa5a5a5a5` 系（FreeRTOS 任务栈填充）——提示"释放/复用 + 悬垂"
   或"越界写入了带栈填充字节的块"；
3. 用**对照组**缩小范围（同目录好曲不崩 → 文件内容相关）；
4. 开 `CONFIG_HEAP_POISONING_COMPREHENSIVE` 复现，让越界写自己报出写入者；
5. 若指向"垃圾数据进了解码器/解析器"——在入口加**结构性门禁**而不是依赖
   解码器容错（解码器对"随机但偶发合法"的输入未必安全）。

## 8. 附：为什么 Helix 遇到问题文件不返回错误，而是直接破坏堆？

> 用户追问。三层原因叠加：**MP3 格式本身没有强校验、解码器的内存是按"合法编码器
> 能产出的数据"精算的、C 语言没有越界保护**。注意：证据链证明的是"崩溃发生在解码
> 阶段 + 堆被破坏"，行级"现行犯"并未抓到（见 8.4），Helix 内部写穿是强推断。

### 8.1 MP3 格式决定了"解码器没法知道这是垃圾"

- MP3 帧默认**没有 CRC、没有文件级校验和**（CBR/VBR 都无），解码器只能判断
  "帧头字段合不合法"。
- 随机字节凑出"字段全合法"的帧头概率约 1/2^16~1/2^20；坏文件里混着**其它文件的
  真实字节**，完全可能嵌着几个假帧头。对解码器而言那不是错误，只是"有点奇怪的
  音频"，它会继续按规则解析——**错误只有它自己发现才算**。

### 8.2 Helix 的内存按"合法极端值"精算，防的是"普通损坏"而非"构造数据"

解码器自带的设计注释与代码（`libhelix-mp3`）：

```c
/* mp3dec.h —— MAINBUF_SIZE 的设计依据 */
/* max mainDataBegin = (2^9 - 1) = 511
 * max nSlots = 1440 - 9 - 4 + 1 = 1428
 * 511 + 1428 = 1939, round up to 1940 */
#define MAINBUF_SIZE  1940
```

```c
/* mp3dec.c —— 把"历史 bit reservoir + 当前帧数据"拼进固定缓冲 */
memmove(mp3DecInfo->mainBuf, mainBuf + mainDataBytes - mainDataBegin, mainDataBegin);
memcpy(mp3DecInfo->mainBuf + mainDataBegin, *inbuf, nSlots);   /* 写入量 = mainDataBegin + nSlots */
```

- 它假设合法编码器最多产出"511 字节 reservoir + 1428 字节帧数据"；而
  `mainDataBegin`（9 bit，来自帧 side info）与 `bitrate/samplerate`（来自帧头）是
  **两个互相独立的字段**——垃圾数据可拼出"帧头高码率大帧 + reservoir 顶格"等
  超出假设的组合，固定缓冲即被写穿。
- `mainBuf` 嵌在 `MP3DecInfo` 结构体内（`mp3common.h`），该结构体由
  `MP3InitDecoder()` 动态分配 → **解码器内部缓冲写穿 ≈ 直接写堆**，与"UI 堆对象
  里出现 0xA5（FreeRTOS 任务栈填充字节残留）"的观察吻合。

### 8.3 为什么"不立即报错、而是几毫秒后在 UI 里炸"

C 的越界写不抛异常，只是静默改写相邻内存。解码任务（Core1）写完就走，堆已被
悄悄弄坏；直到 Core0 的 LVGL/分配器把坏块用起来才爆（LoadProhibited 出现在
毫不相干的 label 样式刷新里）。复现时也确认：崩溃前**从未打印 `mp3: …Hz`**——
连一帧有效音频都没解出，破坏发生在"找同步/试解坏帧"阶段。

### 8.4 证据边界与为什么选"门禁"而非"修解码器"

- 已证明：崩溃只在该文件进入解码阶段时发生（好曲对照不崩）；门禁让它不进解码器
  后崩溃消失；破坏形态是堆被任务栈填充字节污染。
- 未抓到具体越界写入行：堆毒化在"被破坏块被 free"时才报 CORRUPT HEAP，而系统在
  free 前已崩；行级定位需 gdb watchpoint / 给解码缓冲包 canary 逐帧喂构造数据。
  外壳代码（按 `fi.outputSamps` 写 `stereo_buf` 等）有残余嫌疑但该场景从未解出
  有效帧，嫌疑很小。
- 修法取舍：esp-libhelix-mp3 是第三方老代码（RealNetworks 授权移植），输入空间
  无穷、洞补不完；正解是**信任边界前移**——入口 fail-fast，先证明"这是真 MP3"
  （连续两帧 + 帧长自洽）再放行，垃圾数据到不了解码器，破坏面整体消失。
