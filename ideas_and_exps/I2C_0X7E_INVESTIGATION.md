# I²C0 上那个 0x7E 到底是什么（调查记录）

**结论先说：不是第 6 颗芯片，是总线上已有的一颗芯片对「I²C 保留地址」的假应答。**
本板 I²C0 只有 4 颗从设备（CST820 / AXP2101 / PCF85063 / QMI8658），原理图上没有任何器件在
0x7E；`0x78~0x7F` 整段是 I²C 规范保留给未来协议的地址，合法从设备**不允许**占用。
因此 `i2c_scan()` 已改成只扫 `0x01~0x77`（见 `main/core/hardware/touch.c`），日志里的
`Found I2C device at address 0x7e` 从此不再出现。

- 调查日期：2026-11-14
- 硬件：FakePodNano Pro V1.0（ESP32-S31），原理图 `devkit-fake_pod_nano_pro/hardware/FakePod_S31_Schematic_V1.0.pdf`（9 页）
- 起因：开机 I²C 扫描日志里除了 4 颗已知设备外，多出一条 `Found I2C device at address 0x7e`

---

## 1. 原理图侧的证据：板上没有 0x7E 这个器件

把 V1.0 原理图 9 页逐页看完（USB-C/SD、DAC 电源、CS43131 模块、LCD、MIC、PWR、S31、IMU、IO 安排、RTC），
I²C 总线只有两条，全部器件如下：

| 总线 | 引脚 | 上拉/串阻 | 器件 | 7-bit 地址 |
| --- | --- | --- | --- | --- |
| I²C0 | SDA GPIO48 / SCL GPIO47 | 2.2 kΩ 上拉到 ESP_3V3（R27/R28）+ 33 Ω 串阻（R17/R18） | CST820（贴在屏排线上的触摸 IC） | 0x15 |
| I²C0 | 同上 | 同上 | AXP2101（PMU，PWR 页 SDA/SCK → `TP_SDA`/`TP_SCL`） | 0x34 |
| I²C0 | 同上 | 同上 | PCF85063（RTC，RTC 页 → `IMU_I2C_SDA/SCL` → 与 `TP_SDA/SCL` 同网） | 0x51 |
| I²C0 | 同上 | 同上 | QMI8658（IMU，IMU 页 → `IMU_I2C_SDA/SCL`） | 0x6B |
| I²C1 | SDA GPIO55 / SCL GPIO54 | 经 TXS0102DQER（J2）做 1V8↔3V3 电平转换 | CS43131（DAC，DAC 页 `SDA_IV8`/`SCL_IV8` → 译成 R22/R23 2.2 kΩ 上拉到 1V8） | 0x30 |

关键点：

- **IMU/RTC 与触摸不是两条总线**：IO 安排页把 `TP_SDA↔IMU_I2C_SDA`、`TP_SCL↔IMU_I2C_SCL` 直接并成同一网络，
  所以 AXP2101 / PCF85063 / QMI8658 / CST820 确实共用一个总线实例（与 `hardware_v1.md` §3 一致）。
- **CS43131 在另一条总线上**：它的 1V8 侧经 TXS0102 到 GPIO54/55（I²C1），物理上不可能在 I²C0 上应答。
- 全图没有任何 **I²C 从设备被配置成 0x7E**：没有地址选择跳线、没有 IO 扩展器、没有第二颗 EEPROM/传感器。
  LCD（CO5300）是纯 QSPI，USB-C 只有 ESD 阵列（H5VL10B），SD 是 SDMMC 4-bit，麦克风是 PDM。

## 2. 0x7E 在协议里的身份：保留地址

7-bit 地址 `0x7E = 1111_111b`，在线上的字节是 `0xFC`（写）/`0xFD`（读）。I²C 规范把
`1111_0xx` 划给 **10-bit 地址前缀**，`1111_1xx`（0x78~0x7F）整段**保留给未来协议**；
其中 0x7E 在 I³C 里是**广播地址（broadcast）**，所有 I³C target 都必须应答它。
也就是说：**"扫到 0x7E" 这件事本身就是"某个器件在保留地址上表了态"，不可能是一颗正规矩器件。**

同类现象在别的板子上也有先例：微雪 ESP32-S3-Touch-LCD-2.1 的 FAQ 直接把
「0x15, 0x20, 0x51, 0x6B, 0x7E」列为"总线上已被占用的地址"，而那块板子的芯片组与本板高度重合
（CST820 + PCF85063 + QMI8658 + AXP2101）—— 说明这是该芯片组的共性，不是本板个例。

## 3. 实测：两个互相独立的 master、四轮上板实验

为了排除"ESP-IDF 新 I²C 驱动自己记错了"，实验分两条完全独立的路径：

- **A. 硬件外设**：`i2c_master_probe()`（工程里 `i2c_scan()` 原有的调用）；
- **B. 软件位翻转（bit-bang）**：把 GPIO47/48 配成开漏输入输出，手写 START/STOP/读写时序，
  完全不经过 I²C 外设（半周期 5 µs≈100 kHz 与 50 µs≈10 kHz 两档）。

| 实验 | 结果 |
| --- | --- |
| A：扫描前先探 0x7E（总线刚初始化、之前无任何传输） | **ACK 5/5** |
| A：探板上不存在的 0x2A / 0x3C / 0x70 / 0x77 | **全部 NACK（0/3）** |
| A：整轮 1~126 扫描 | 命中 0x15 / 0x34 / 0x51 / 0x6B / **0x7E**，无其它 |
| A：扫描后复探 0x7E | **ACK 5/5**（与扫描顺序无关） |
| B：位翻转全量扫 1~127 @100 kHz | 同样只有 0x15 / 0x34 / 0x51 / 0x6B / **0x7E** |
| B：0x7E 慢速重试 @10 kHz | **ACK 3/3**（不是时序边际，10 kHz 下依然应答） |
| B：把 CST820 拉进复位（TP_RST=0）后重探 | 0x15 **消失**；0x34/0x51/0x6B 仍在；**0x7E 仍然 ACK** |
| A：对 0x7E 读 1 字节 | **超时**（`I2C transaction timeout`）→ 之后 `I2C bus is still busy` / `clear bus failed`，总线需恢复 |
| B：对 0x7E 写 1 字节（地址 + 数据） | 地址 **ACK**、数据字节 **NACK** |
| B：对 0x7E 写寄存器地址再读 | 失败（数据字节 NACK） |
| B：指针直读（`[S][addr|R][读1B]`） | 0x6B 与 0x7E **读到同一个值**（同一次开电内都是 0x7C；另一轮开机 0x7E 读到 0x05） |

几条能直接下结论的：

1. **ACK 是真实发生在 SDA 线上的**，不是驱动误判 —— 两个完全不同的 master 都看到它，
   而且 100 kHz / 10 kHz 两档都有。
2. **它是"地址选择性"的**：随便挑的 4 个空地址全部 NACK，只有 0x7E 应答 →
   不可能是总线漏电/上拉问题，而是**某颗芯片真的在回应这个地址**。
3. **应答者不是触摸芯片**：TP_RST 拉低后 0x15 立刻消失，0x7E 照旧 ACK。
4. **0x7E 没有可用的寄存器接口**：地址字节被 ACK，但后续数据字节被 NACK，
   读操作会把硬件 I²C 外设直接卡到超时（这是"假应答"的典型特征 —— 只认地址、不认数据）。
5. **它背后的寄存器是"共享"的**：同一开机周期里对 0x6B 与 0x7E 做指针直读拿到同一个字节
   （0x7C），而不同开机周期 0x7E 又会读到不同值（0x05 / 0x7C）→
   说明 0x7E 不是一个独立器件，而是**某颗已有芯片的另一个"入口"**。

### 3.1 最可能是谁

剩下的嫌疑人只有 AXP2101 / PCF85063 / QMI8658（触摸已排除，CS43131 不在本总线）。
现有线索都指向 **QMI8658**：

- 指针直读 0x6B 与 0x7E 得到**同一个字节**，说明两者背后是同一颗硅片、同一套寄存器指针；
- 某轮开机 0x7E 的指针直读返回 `0x05`，正是 QMI8658 的 `WHO_AM_I`（reg 0x00）值
  （AXP2101 的 reg0 是 STATUS1，上电典型值 0x20；PCF85063A 的 reg0 是 Control_1，复位值 0x00 —— 都对不上）；
- 微雪同芯片组板子也把 0x7E 记为"已占用"。

未做的一步（需要示波器或逐颗断电，成本高、收益低）：把 IMU 单独断电再探 0x7E。
由于**工程里从不访问 0x7E**，这一点不影响任何功能，故未继续深挖。

## 4. 代码侧处理

`main/core/hardware/touch.c` 的 `i2c_scan()` 从 `addr < 127` 改为 `addr < 0x78`，
即**不再扫 0x78~0x7F 这段保留地址**。这既符合 I²C 规范（合法 7-bit 地址就是 0x00~0x77），
也永久消掉了这条误导性日志。

```
I (1247) touch: Found I2C device at address 0x15
I (1250) touch: Found I2C device at address 0x34
I (1255) touch: Found I2C device at address 0x51
I (1260) touch: Found I2C device at address 0x6b
I (1265) touch: I2C scan completed.
```

> ⚠ 反面教材：**不要**为了"消除幽灵设备"而在扫描里加 `if (addr == 0x7E) continue;` 这种特判 ——
> 那样只是把现象藏起来，而且下次换一颗芯片、换一个保留地址又会出现。
> 按规范限定地址范围才是根治。

## 5. 以后想复现这套实验

临时把下面这些插进 `touch.c`（**必须在 `i2c_new_master_bus()` 之前**做位翻转扫描，
因为一旦外设接管引脚就不能再手动翻转；实验完记得 `git checkout` 撤掉）：

1. `gpio_config()` 把 GPIO47/48 设为 `GPIO_MODE_INPUT_OUTPUT_OD` 并 `gpio_pullup_en()`；
2. 开漏语义：写 1 = 释放（靠外部 2.2 kΩ 上拉），写 0 = 拉低；
3. START：SDA 高→低（SCL 高时）；STOP：SCL 高时 SDA 低→高；
4. 每个字节 8 个时钟，第 9 个时钟释放 SDA 读 ACK（读到 0 = ACK）；
5. 释放 SCL 后要**等 SCL 真的变高**再采样（从机可能拉低做时钟延展，否则读到半个时钟）；
6. 对比实验设计是关键：① 扫描前先探目标地址（排除"扫一圈之后才出现"）；② 同时探几个必然不存在的地址
   （排除驱动/总线假象）；③ 拉低目标的 RST 再探（定位应答者）；④ 换速度档（排除时序边际）。

硬件外设侧的对照只需 `i2c_master_probe(bus, 0x7E, 50)`；注意**不要**用
`i2c_master_receive()`/`transmit_receive()` 去读 0x7E —— 会把总线卡到需要 `clear bus`，
后面所有设备的初始化都可能跟着失败。

## 6. 顺手记下的其它 I²C 事实（本次核对原理图时确认）

- I²C0 的 4 颗设备全部挂在 `TP_SDA`/`TP_SCL` 这一对网络上，**只应建一个总线实例**（工程已如此）。
- 上拉是 2.2 kΩ 到 **ESP_3V3**（不是 1V8），并带 33 Ω 串阻；400 kHz 没问题。
- CS43131 的 I²C 在 **1V8 域**，必须经 TXS0102 电平转换（J2），对应 GPIO54/55（I²C1）；
  DAC 页另有 1V8 侧的 2.2 kΩ 上拉（R22/R23）与"这是1V8，用来给CS43131 I2S1 I2C 通讯"的图注。
- 触摸 INT/RST 是 GPIO45/46，PMU 中断是 GPIO49（经 Q2 BSS138W 电平转换后为 `ESP_PMU_IRQ`）。
