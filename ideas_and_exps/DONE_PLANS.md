## 3. 神奇的随机算法 ✅ 已完成

新增随机播放模式（无限确定性随机播放列表，设计文档见桌面《随机播放.md》）：
设置页「顺序/随机」开关已接播放引擎；随机序列由无数个"块"（全部歌曲的
随机排列）首尾相连组成，只需保存一个 uint64 逻辑位置即可完整恢复现场。

实现要点（2026-09-01 完成）：
- `core/player/shuffle_player.{c,h}`：分块 + 确定性洗牌（Fisher-Yates）。
  块索引位混合 + 黄金比例常数作为 xorshift32 种子；仅缓存当前块（O(N)），
  跨块按需重洗；**缓存元素按歌曲数缩水**（N≤65535 用 uint16_t，省一半 RAM）；
  提供 `get_index_at(position)`、`find_in_block(block, global)`、
  `random_start()`（esp_random 拼 64 位真随机起点）。
- `player_controller`：随机模式下 上一曲/下一曲/自然播完 均按随机序列
  位置 ±1 推进（无限序列无边界，非顺序列表相邻曲目）；随机位置经
  config_store 持久化（uint64 拆高/低 32 位 + valid 标志）。
- **随机列表固定为当前播放目录/歌单**（与循环模式无关）：随机位置 P 映射
  到"目录内歌曲索引"（P % N），再换算全局下标 = dir_start + 索引；随机
  序列永不跨出当前目录。仅当用户从其它目录选歌时随机列表随之切换。
- 随机 + 单曲循环：自然播完保持单曲循环（原地重播），但**手动切歌始终走
  随机序列**（下一曲/上一曲 = 随机位置 ±1，与循环模式无关，仍在当前目录内）。
- **随机位置重置时机**（仅这三处重新生成，其余一律保存以便恢复）：
  1. 用户从列表指定播放歌曲（`play_song`）→ 随机取新块并在块内定位到
     该歌曲，当前位置 = 新块索引 × N + 块内偏移；
  2. 切换列表后从新列表选歌（同上，走 play_song）；
  3. 随机播放关闭后再开启 → 重新生成随机位置并定位到当前歌曲。
  上一曲/下一曲/自然播完/暂停/停止/开机恢复均保持并保存随机位置，
  断点续播回到同一首歌、同一序列（开机走 CMD_PLAY_SONG_RANDOM 不重生成）。
- 随机 + 单曲循环：自然播完原地重播；随机模式下循环模式仅单曲循环生效。

## 4. 适配 3 秒关机芯片 ✅ 已完成

成品机电源侧有长按 3 秒硬断电的关机芯片，**与 A 键（GPIO48）复用同一按键**：
长按超过 3 秒由硬件直接断电/开机，固件无法参与断电本身，只需在断电前完成保存。

实现要点（2026-09-01 完成）：
- **两种伪关机行为**（`core/utils/fake_shutdown.c` 统一流程 + 两个入口）：
  - `fake_shutdown_enter()` **普通伪关机（息屏）**：睡眠定时器/双按触发，
    关尽外设含显示屏（主动关屏省电），deepsleep，B 键（GPIO0）唤醒重启；
  - `fake_shutdown_wait_power_off()` **A 键长按 2s 伪关机（不息屏）**：
    配合电源侧 3 秒关机芯片——显示「正在保存配置」→ 保存配置、优雅停播 →
    显示「继续按上键以彻底关机\n或者按下键取消关机」→ 停外设（**不关屏**，
    画面定格在提示上）→ deepsleep；用户继续按住 A 键满 3s 即由硬件断电
    （屏幕靠**断电自然熄灭**，向用户展示"关机已完成"，主动关屏会让用户
    分不清是否真的关机）；若未断电，按 B 键（GPIO0，RTC GPIO）唤醒即
    "取消关机"（唤醒 = 重启，走正常开机流程恢复上次播放位置）。
- `button_service` 增加**长按事件**（`BUTTON_EVENT_A_LONG`/`B_LONG`，
  阈值 `BUTTON_LONG_PRESS_MS=2000` 可调）：按住满阈值即上报（无需抬起）；
  长按后抬起不再补报单击；双按交互期间不触发长按；**开机时已被按住**的键
  （如长按 3s 开机后未及时松手）首次抬起前不触发长按，避免"开机即误判
  关机"。
- 伪关机流程加 `s_shutting_down` 互斥：长按关机进行中又被双按/睡眠定时器
  触发时直接返回，避免并发停外设重复删除 I2C/SDMMC 驱动崩溃。
- ⚠ **踩坑：按键任务栈溢出**。初版在按键任务（`button_svc` 栈 3KB）里直接
  执行关机流程，创建 LVGL 提示覆盖层 + `lv_refr_now` 渲染调用链很深，
  触发 `A stack overflow in task button_svc` 自动重启（实测长按即崩）。
  已改为**独立关机任务**（`fake_shutdown_task`，8KB 栈、优先级 6）：
  两个入口只做防重入 + 创建任务后立即返回，顺带消除了睡眠定时器路径
  （`sleep_timer` 任务栈 2KB）的同款隐患。
- ⚠ **长按阈值 2000ms 实测偶发"按了没提示"**：用户按满 3s 时提示只显示约
  1 秒甚至一闪而过（伪关机流程本身还要耗时）。改为 **1200ms**，
  提示显示窗口约 1.8s。
  （2026-11 更新：该阈值已从 Kconfig 移到 `ui/key_handler.h` 的宏
  `KEY_A_LONG_PRESS_ON_MS` / `_OFF_MS`，并分亮屏 1200ms / 息屏 900ms 两档。）
- 实测（2026-09-01）：长按 1.2s 触发 → 提示定格 → 继续按住 3s 硬件断电；
  中途按 B 键唤醒 → 重启恢复关机前播放位置（精确到秒）；流程总耗时约
  340ms，远小于 3s-1.2s=1.8s 的断电窗口。
- 断电时序：2s 触发 → 1 秒窗口内完成 NVS 保存/停播/停外设（耗时足够）；
  3s 硬件断电。屏幕定格提示（AMOLED 存储型显示，deepsleep 下保持显示；
  断电自然熄灭）。
- ⚠ 提示文字「正在保存配置/继续按上键以彻底关机/或者按下键取消关机」在
  **精简版字体**（`CONFIG_UI_SYSTEM_FONT_FULL=n`，调试用）中缺字，
  正常使用完整版字体（默认开启）可正常显示。

## 5. 息屏播放模式 ✅ 已完成

双按不再是伪关机，改为息屏/亮屏切换；息屏期间停止 LVGL 与触摸、降低 CPU
主频；新增无操作（按键/触摸）超时自动息屏。伪关机仅保留给睡眠定时器
（以及 A 键长按"等待断电"关机）。

实现要点（2026-09-01 完成）：
- 新增 `core/utils/screen_sleep.{c,h}`：息屏状态机 + 后台超时检测任务。
  - **息屏**：持 LVGL 锁把亮度置 0（全黑，AMOLED 存储型显示保持最后帧）
    → 挂起 LVGL（`lvgl_port_suspend`：停止 tick 计时 + 挂起任务，刷屏与
    触摸轮询一并停止）→ CPU 固定降频到 **80MHz**；
  - **亮屏**：CPU 恢复 240MHz → `lvgl_port_resume`（恢复任务 + 重启 tick，
    LVGL 时间从暂停点继续无跳变）→ 持锁恢复用户配置亮度；
  - **无操作超时**：独立任务（Core1，优先级 1）每秒检查，亮屏且距最近
    活动（按键/触摸）超过配置时长 → 自动息屏；超时经 config_store 持久化
    （默认 30 秒）。
  - ⚠ **降频方式**：最初用 esp_pm DFS（释放 CPU_FREQ_MAX 锁、空闲自动降频），
    实测任务上下文与 ISR 采样均观察不到降频（DFS 仅在双核都空闲时降频，
    采样点难以落在空闲期；且核心常因周期性任务保持活跃）——改为
    `esp_pm_configure` 强制 max=min=目标值直接**固定频率**（息屏 80 / 亮屏
    240），mem_monitor 可直接看到 freq 变化。若 80MHz 下 MP3 解码卡顿，
    把 `PM_CPU_FREQ_OFF_MHZ` 改为 160。
- `lvgl_port` 改造：`lvgl_port_suspend` 现在同时停止 lv_tick 定时器，
  新增 `lvgl_port_resume`（恢复任务 + 重启 tick）；触摸事件订阅改为
  **多订阅者数组**（触摸测试 + 息屏活动检测共用，`lvgl_port_unregister_touch_cb`
  可注销）。
- `config_store` 新增"自动息屏超时"（`screen_off`，NVS，默认 30 秒，
  范围 5~3600）。**暂不在设置页展示**：九宫格保持 3 功能格 + 6 空位，
  该设置项后续放独立的不常用设置页（用户反馈，见本文件"其它"说明）。
- `sdkconfig.defaults` 开启 `CONFIG_PM_ENABLE=y`（esp_pm 固定频率）与
  `CONFIG_ESP_TIMER_SUPPORTS_ISR_DISPATCH_METHOD=y`（performance_monitor
  用 ISR 定时器采样 CPU 频率；ESP32-S3 的 APB 恒 80MHz，I2S/SPI 时钟不受
  CPU 降频影响）。
- `performance_monitor` 每 2 秒输出增加 `freq=XMHz(idle:YMHz)`：X 为任务
  上下文读到的频率，Y 为 esp_timer ISR 采样值——固定频率模式下两者一致
  （亮屏 240 / 息屏 80），用于验证降频生效。
- ⚠ **踩坑：自动息屏栈溢出**。初版 `screen_sleep_task` 栈 2KB，到点自动
  息屏时在任务内直接调用 `screen_sleep_enter()` → `esp_pm_configure`
  调用链很深（do_switch → 跨核 CCOMPARE 同步 → ESP_LOGI 格式化），触发
  `A stack overflow in task screen_sleep` 自动重启；手动息屏走 button 任务
  （3KB 栈）未爆，极具迷惑性。已把 `SCREEN_SLEEP_TASK_STACK` 加到 8KB
  （与 fake_shutdown 任务同规格），实测自动息屏不再重启。
- **息屏+暂停超时自动伪关机**（省电，2026-09-01 增加）：仅当设备处于
  **息屏且暂停**状态持续超过 `CONFIG_PAUSE_AUTO_SHUTDOWN_MIN` 分钟
  （Kconfig，默认 10，0=关闭）→ 普通伪关机（deepsleep，B 键/双按唤醒）。
  亮屏时暂停不计时（用户在看屏幕随时会操作）。检测复用 screen_sleep 的
  每秒任务。
- **开机恢复播放状态（记忆功能）**（2026-09-01 增加）：`config_store`
  新增 `was_playing`（NVS）——伪关机（普通/A 键长按）前由
  `player_controller_save_last_position` 记录"当时是否在播放"；开机按记忆
  恢复：关机前在播放 → 自动播放；关机前已暂停/停止 → 恢复当前歌曲但不
  自动播放（紧跟 CMD_PAUSE 停在暂停态，避免开机突然出声）。配合息屏+暂停
  超时关机，用户双按唤醒后看到的是暂停界面而非自动出声。
  ⚠ **不记忆秒数位置**（NightPlayer 原版机制）：只记当前歌曲，开机从歌曲
  开头开始（`last_pos` 恒为 0，恢复流程不再 SEEK）。
- 息屏状态下睡眠定时器到点仍走 `fake_shutdown_enter` 普通伪关机（兼容息屏
  中 LVGL 已挂起/屏幕已黑的状态，deepsleep 前重复挂起无副作用）。

## 6. 更新按键逻辑 ✅ 已完成

上键 A（GPIO48，与 3 秒关机芯片复用，长按会关机）；下键 B（GPIO0，
可安全长按）。亮屏/息屏两套按键映射，由新增 `ui/key_handler.{c,h}`
统一分发（main.c 不再直接处理按键）。

实现要点（2026-09-01 完成）：
- **亮屏状态**：A 短按 = 音量+1；B 短按 = 音量-1；A 长按 = 伪关机（等待
  断电，保持原提示定格）；B 长按 = 音量一次性 -10；双按 = 息屏。
- **息屏状态（黑屏盲操作，不亮屏）**：A 短按 = 播放/暂停；B 短按 = 下一曲；
  B 长按 = 上一曲；A 长按 = **先亮屏再伪关机**（点亮屏幕显示"正在保存配置/
  继续按上键关机"提示，满足计划要求）；双按 = 亮屏。
- **所有按键事件都记为用户活动**（`screen_sleep_note_activity`），刷新
  自动息屏计时。
- **B 键长按阈值 600ms**（`BUTTON_B_LONG_PRESS_MS`）：A 键 1200ms
  （与 3 秒关机芯片配合；2026-11 起为 `ui/key_handler.h` 的
  `KEY_A_LONG_PRESS_ON_MS`，另加息屏档 `_OFF_MS`=900ms，不再走 Kconfig）；
  B 键可安全长按（亮屏=音量-10、息屏=上一曲），缩短阈值提升响应
  （2026-09-01 用户要求）。长按与双按判定机制互斥，无冲突。
- **音量调节线程安全**：按键回调（button 任务）里先持 LVGL 锁再调
  `config_store_set_volume`（其变更回调会操作设置页/通知栏 LVGL 对象），
  再调 `audio_set_volume_level` 写 CS43131；顺序必须是**先写硬件再持久化**
  （config 变更回调会读 `audio_get_volume_level()`，顺序反了显示会滞后）。
- **音量档位化**（2026-09-01 完成，替代原"压到 0-30 并做曲线映射"计划）：
  音量 0~30 档——0=静音（CS43131 音量寄存器直接写 0xFF，不走静音控制位），
  1~30 线性映射 20%~80%（每档约 2.07 个百分点），默认 20 档；短按 ±1 档、
  B 长按 -10 档；`config_store` 的 `volume` 字段改为存档位（旧 0~100 百分比
  开机自动迁移，20%~80% → 1~30 档并写回 NVS）；状态栏音量图标固定为 mid、
  只显示档位数字。
- **状态栏音量即时刷新**：app.c 订阅 config_store 变更回调，按键调音量后
  立即更新状态栏音量显示（原 5 秒周期刷新）。
- 唤醒防循环（开机 1.2 秒忽略按键）与按键服务"开机初始按压不触发长按"
  机制保留，随按键逻辑一并移入 key_handler。

## 7. 添加ID3读取标题、艺术家和专辑信息，以及封面 ✅ 已完成

考虑到封面大小不一，为了方便，改成一个电脑程序扫描后，重新编码调整大小后放在 .ecov 文件夹中，读取它当封面。没有或者失败就默认，下位机干不了的事情就交给上位机去干

实现要点（2026-09-01 完成）：
- 上位机（桌面 TestMP3PictureInfo 工程，NightPlayerNanoInfoScanner.exe）扫描
  SD 卡每首 MP3，把标题 / 艺术家-专辑副标题 / 回放增益 / 封面（重编码为
  460x460 JPEG，黑底居中）按固定二进制格式写入 `/sdcard/.ecov/<相对路径>.npd`。
- `core/music/song_meta.{c,h}`：.npd 二进制解析（小端：int32 标题长度+UTF-8
  标题、int32 副标题长度+UTF-8 副标题、uint32 增益 16.16 定点、int32 JPEG
  长度+数据）。路径换算：`/sdcard/x.mp3` → `/sdcard/.ecov/x.mp3.npd`。
- `core/image/cover_jpeg.{c,h}`：esp_jpeg（tjpgd 软件解码）把 JPEG 解码为
  RGB565（swap_color_bytes=1 高字节在前，匹配 LV_COLOR_16_SWAP），封装成

.eq文件存放在SD卡根目录的.musicfx文件夹里，格式是：

第一个数字是fCenter，浮点数，范围16-20000，

目前处理链路里挂了一个回放增益，是直接进行的整数运算。
后续需要考虑：
Int16 -> 浮点数 -> 乘以EQ增益 -> 级联参与处理 -> 乘以回放增益（需要从0-65536缩放回0f-1f，注意数字有无符号之间的转换） -> Clamp -> 转成32位并输出

## 12. 研究底噪成因，以及遮蔽底噪的可能性 ✅ 已完成

> 2026-09 初步实验（详见 `ideas_and_exps/底噪研究记录.md`）：SD 卡频率与底噪无关
> （40/20MHz 读数一致）；底噪分两条路径——① 亮屏状态相关（CPU 240MHz/显示活动，
> 息屏掉出听域），② 与具体卡相关（问题卡 64GB 息屏仍有 ~-59dB，换卡可消除）。

目前在播放时，会有 -51dB（相对于音量15的 0 dBTP）的底噪，观察后发现如下规律：
1. 需要是灵敏度较高的耳机
2. 该底噪在息屏和亮屏下都有，且亮屏时音调更高（大约一个半的八度，如果前者是Do的话，后者就是高八度的Sol）更难以察觉（可能跟核心频率有关？音调变化和核心频率变化吻合）
3. 底噪的特性是断断续续的吱吱声，播放时按照固定的节律响起，当切换歌曲时会有一声较长的吱吱声，然后才是较短的吱吱声，推测和读取SD卡有关？
4. 亮屏时的吱吱声和息屏时的吱吱声节奏几乎相同，只有音调的区别
5. 暂停时没有底噪

研究方向：
1. 研究是否和读卡有关，例如改变SD卡频率
2. 刷入其他的固件，测试不同固件的底噪

## 19. Bug：当拖动了进度后，点击暂停不会暂停，再点一次才会暂停 ✅ 已完成

现象：播放中拖动进度条松手（seek）后，点一次暂停按钮无效，需再点一次才真正暂停。

根因（2026-09 定位）：`mp3_player_seek()`（`core/hardware/audio/mp3_player.c`）无论当前播放还是暂停都
**无条件 `xSemaphoreGive(s_resume_sem)`**。播放中调用时播放任务并没有阻塞在暂停信号量上，这次 give
让二进制信号量残留为"满"；随后第一次点暂停，播放任务在暂停分支把状态置 `MP3_STATE_PAUSED` 后的
`xSemaphoreTake` 立即成功 → 暂停被瞬即恢复（表现就是"点了没暂停"）；第二次点暂停时信号量已空，
才真正暂停。与"拖动进度后第一点无效、第二点生效"的现象完全吻合。

修复：seek 仅在 `MP3_STATE_PAUSED`（播放任务确实阻塞在 resume_sem 上等唤醒）时才 give，播放中 seek
由解码循环轮询 `s_seek_requested` 自行处理，不再污染信号量。暂停态拖动进度的原有行为（唤醒播放任务
并跳到新位置）不受影响。

实测：一次点击即暂停，通过。

## 20. Bug：偶尔会出现标题和副标题变成文件名和文件夹的情况，但封面又正常加载，而且切一下有概率没有，怀疑是两处设置标题的地方是并行进行的，设置fallback标题的后执行了 ✅ 已完成

现象：切歌后（概率性）标题/副标题变成文件名/文件夹名，但封面却正常加载；再切一下有概率恢复。

把 `s_meta_title` **清空**，然后再同步读 `.npd` 解析元数据（读文件几十~几百 ms 的阻塞窗口）。期间
UI 侧 500ms 轮询（player_ticker → now_playing 的 np_refresh_cb）若命中该窗口，`get_status()` 读到
"新歌 + 空元数据"快照 → 标题一次性写成 fallback（文件名/目录名）——而标签只在 `cur_global` 变化时
设置一次，之后不再刷新，标题永久卡在 fallback。封面由独立后台任务（cover_load_task）加载并做
"当前歌曲未变"校验，不受该窗口影响，故封面始终正常（与用户观察一致）。

修复（采纳用户建议的方案）：封面加载任务本身完整解析了 `.npd`（`song_meta_t` 含 title/subtitle），
且它的请求由"写入 fallback 的那次 UI tick"触发、完成必然晚于该 tick——"封面解码完成"即元数据可靠
就绪的时机。`cover_load_task` 在换封面（成功解码 / 回退默认封面两条路径）的同一持 LVGL 锁区间，用
meta 字段补写标题/副标题（无该字段时回退文件名/目录名，`player_controller_status_t` 已校验为新歌），
并补了一次解码后的二次"歌曲未变"校验，防解码期间又切歌。无 `.npd` 的歌曲 fallback 本就是正确显示，
无需纠正。

实测：快速连续切歌标题/副标题均正确，通过。

## 21. Bug: 低电压自动关机似乎没有生效？ ✅ 已完成（机制正常，定稿阈值 3.45V）

现象：一夜播放到 3.1V 仍在播放，低电压自动伪关机未触发。

排查结论（2026-09）：自动关机机制本身**无缺陷**（power_service 每秒低电检查 +
`CONFIG_LOW_BATTERY_SHUTDOWN_SEC=60` 持续计时，代码与构建配置均正常）。真正的根因在电池放电曲线：
锂电 ~3.5V 之后进入拐点、电压骤降极快——电池电压日志显示 **3.1V 只有一条采样记录**，即 60 秒持续
低电计时窗口尚未走完电压就已跌出范围，原阈值 3.2V 实际"来不及触发"（不是检查逻辑问题）。

处理与验证：
- 先临时把共用阈值 `BATTERY_CRITICAL_LOW_MV`（`core/hardware/battery.h`，开机拒启与运行中自动关机
  共用同一宏）调为 4.1V 实测：插电 ~4.15V 满足开机条件正常启动，拔电后 ~4.05V < 4.1V → **亮屏与
  息屏状态下运行中均于 60 秒后自动伪关机**，拔电冷启动亦正确拒启——机制确认无误。
- 正式值定稿 **3.45V（3450mV）**：位于放电拐点前的平台段，持续低电计时可靠触发；与 0%
  （BAT_EMPTY_MV=3.0V）留 450mV 余量。取值缘由已写入 battery.h 注释。

## 28. 内部 RAM 耗尽：非实时任务栈迁到 PSRAM ✅ 已完成

**问题**（长期潜伏，非某次改动引入）：开机末期内部 RAM 仅剩约 4~5KB、
最大连续块约 8.6KB，任何新建任务都会失败。已观察到的症状：
`create power service task failed`（自动息屏/低电关机全失效）、设置菜单
"重新扫描"点了没反应（无法分配栈内存）、`performance_monitor` 的
`mem_monitor`/`cpu_coll0`/`cpu_coll1` 起不来（串口不再打印 MEM 行）。

**根因**（实测数据见 `PSRAM_TASK_STACK.md`）：`SPIRAM_USE_MALLOC=y` +
`SPIRAM_MALLOC_ALWAYSINTERNAL=16384` 下**小于 16KB 的分配优先走内部 RAM**，
而 LVGL（`LV_MEM_CUSTOM=stdlib`）的控件/样式/缓存单次分配都很小，于是
222KB 内部 RAM 被大量小对象瓜分（启动 273KB → 开机完成约 19KB），PSRAM
反而用不上。与 0.9.0.0 alpha 3 对比确认该状况在 alpha 3 就已存在
（当时 performance_monitor 已经起不来），并非新引入。

**方案**（2026-09 完成）：
- 新增 `core/utils/task_psram.{c,h}` 的 `task_create_psram_stack()`：
  先 `xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_SPIRAM)`，失败自动
  回退内部 RAM（调用方无需分支）；TCB 仍在内部 RAM（约 100B/任务）。
- `sdkconfig.defaults` 显式加 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y`。
- 迁移清单（常驻净省约 12KB）：`mem_monitor`、`cpu_coll0/1`、`batt_log`、
  `rescan`(4KB)、`dev_restart`、`cover_load`、`power_svc`、`touch_init`。
- 保持内部 RAM：`LVGL`、`mp3_play`/`mp3_out`、`button_svc`、
  `player_ctrl`/`deep_worker`/`sleep_timer`（实时/低延迟/主路径）、
  `boot_scan`(32KB，扫描要擦写分区 → munmap 关缓存，PSRAM 栈会 assert；
  开机早期内部 RAM 尚有约 130KB，内部栈可分配）。
- 实测：内部空闲 4.5KB → **16~17KB**；MEM 行恢复输出，stk 行可见
  `mem_monitor=1968 cpu_coll0=348 cpu_coll1=376`（HWM 余量正常）；
  自动息屏/重新扫描/封面加载/触摸初始化均正常。
- 后续新建后台任务**默认用 `task_create_psram_stack`**；判断"是否又紧张"
  看 `MEM:` 行的 `iram=` 列与最大连续块（详见 `PSRAM_TASK_STACK.md`）。

## 29. 重新扫描崩溃 + 任务无法创建 ✅ 已完成

**两个连锁问题**（均由第 28 点的迁移暴露/引入）：

1. **崩溃**：`rescan` 任务栈迁到 PSRAM 后，点"重新扫描"立刻 panic：
   ```
   assert failed: esp_cache_freeze_caches_disable_interrupts esp_cache_utils.c:96
   (s_task_stack_is_sane_when_cache_frozen())
   ...
   pldata_munmap → esp_partition_munmap → esp_mmu_unmap → 关缓存
   ```
   根因：卸载 pldata mmap 会**关闭外部内存缓存**，此时 PSRAM 不可访问，
   IDF 要求当前任务栈必须在内部 RAM（`esp_cache_utils.c` 的断言）。

2. **任务创建失败**：改用内部栈后 `create rescan task failed`——实测
   内部空闲约 21KB 但**最大连续块只有 8180 B < 8KB 栈需求**（差 12 字节），
   先释放 cover_load/sleep_timer 也腾不出更大连续块（日志实测 8180 → 8180）。

**方案**：
- `rescan` 任务栈仍放 **PSRAM**（4KB，`task_create_psram_stack`）；
- **关缓存的那段委托给 deep_worker**（内部栈）执行：
  `deep_worker_call(rescan_do_deinit)` → `player_controller_deinit()`
  （停播放 + playlist_deinit → munmap）+ `playlist_store_invalidate()`
  （擦列表头）；
- deep_worker 栈 **8KB → 12KB**（原 HWM 7436/8192 余量不足以叠加该链；
  实测新 HWM 11520/12288）；
  ⚠ **该 12KB 改动已在第 31 点回退为 8KB**（12KB 内部栈在开机末期碎片化下
  创建静默失败，反而导致息屏/亮屏延迟 5 秒）——此处保留当时的记录。
- 确认重扫时仍释放 `cover_load`（`now_playing_release_cover_task`）与
  `sleep_timer`（`sleep_timer_release_task`）——它们马上要重启、职责已无意义，
  顺带避免重扫途中睡眠定时误触发；
- 显式约束写入文档/注释：**凡调用链含 mmap/munmap、esp_flash 擦写、
  pldata_write/erase 的任务，栈必须在内部 RAM**（见 `PSRAM_TASK_STACK.md` 2.4）。

**实测**（COM5 全流程）：确认重扫 → 释放两任务 → 挂起 LVGL →
`player controller released (... playlist unmapped)` → `playlist invalidated
(ESP_OK)` → 重启 → `playlist data invalid, prompt to scan` → 重新扫描成功
（`dirs=171 songs=8816 ret=ESP_OK`），无断言、无崩溃。

## 30. 排查"为何 release 版从未出现内部 RAM 紧张" ✅ 已定位

用户反馈 release 版（alpha 3 起）从未出现内部 RAM 不足，怀疑与 debug 的
堆毒化有关。同代码同设备 A/B 实测（每次只改一个配置项，测量点：
`app_main` 开机完成时 + 性能监视稳态）：

| 配置 | 开机完成 internal | 最大连续块 | 稳态 iram |
|---|---|---|---|
| debug（`HEAP_POISONING_COMPREHENSIVE=y`） | 25,299 B | 14,836 B | 13,679 B |
| debug（同配置，仅毒化改 `DISABLED`） | 50,239 B | 31,744 B | 39,547 B |
| release（毒化 `DISABLED`） | 51,351 B | 31,744 B | ≈39 KB |

**结论**：`CONFIG_HEAP_POISONING_COMPREHENSIVE`（debug 独有）一项就占掉
约 **26KB** 内部 RAM，并把最大连续块从 31.7KB 压到 14.8KB。机制是该模式
给每个分配加带调用栈的元数据头、且**禁止空闲块合并**——LVGL 的成千上万
个小对象把这个代价放大成十几 KB 碎片。所以不是版本差异，而是**堆毒化
配置差异**；debug 是日常烧录配置，第 28/29 点的迁移仍然必要（迁移后
debug 稳态约 13.7KB 够用，关毒化则约 39KB 很宽裕）。

保留 Comprehensive 毒化的理由：它曾在"坏曲播放导致 LVGL 对象崩溃"
（DONE_PLANS 第 16 点）中定位到堆破坏写入者。

**处理（2026-09）**：按用户要求 **debug 默认移除堆毒化**——
`sdkconfig.defaults.debug` 改为 `CONFIG_HEAP_POISONING_DISABLED=y`，
文件内保留注释写明"需要抓堆破坏时临时改回 Comprehensive 再构建"。
第 28/29 点的 PSRAM 栈迁移保留：它让内部 RAM 与毒化开关解耦，
开/关都有余量（关毒化 debug 稳态约 39KB，开毒化约 13.7KB）。

## 31. deep_worker 任务创建静默失败 → 息屏/亮屏延迟 5 秒 ✅ 已修复

**现象**（用户报告）：按键锁屏/解锁有明显延迟，日志
`E deep_worker: deep call timed out after 5000 ms (executor stuck?)`。

**定位**（诊断日志给出决定性线索）：执行器**从未开始执行**任何 fn
（`exec_busy=0`），且超时时 dump 的任务表里**根本没有 `deep_worker` 任务**
——即任务创建失败但代码没检查返回值，仍打了 "deep worker ready"。

**根因**：第 29 点为给"重新扫描"的关缓存段留余量，把 deep_worker 栈从
8KB 提到 **12KB**；而它在 `boot_flow` 之后创建，此时内部 RAM 已高度碎片化
（最大连续块约 8.6KB），12KB 内部栈分配失败 → 任务不存在 → 每次
`deep_worker_call` 都等满 5s 超时后由调用方就地兜底执行（所以功能还能用，
只是慢 5 秒）。

**修复**：
1. 栈回到 **8KB**（实测 HWM 7436/8192 够用）；
2. `deep_worker_init()` 提前到 `app_main` 早期（config_store 之后、硬件
   初始化之前）——此时内部 RAM 充裕（约 240KB 空闲），8KB 必定成功；
3. 检查 `xTaskCreatePinnedToCore` 返回值，失败打 ERROR 并记 NULL；
4. `deep_worker_call` 发现 `s_exec_task == NULL` 立即返回 false（调用方就地
   兜底），不再白等 5 秒；
5. 超时时用 `uxTaskGetSystemState` dump 全部任务状态（名称/状态/优先级），
   便于以后定位"谁堵住了执行器"；
6. 修正 `deep_worker_call` 的槽位清理：只有确实收到完成信号才清空
   `s_pending_fn`，避免超时后"正在跑的执行器"读到下一次投递的函数。

**实测**：`call → exec begin → exec end` 连续出现，息屏 **33ms** 完成
（原 5s）、亮屏 **335ms**（含面板 120ms 唤醒等待）。

## 32. 开机先播一秒旧歌再跳走（DMA 池被 LVGL 绘制缓冲挤干）✅ 已修复

**现象**（用户报告）：开启随机模式后，每次开机都会**先播放约一秒上次记住的
音乐，然后随机跳到另一个队列**里去。

**定位**：随机播放逻辑无缺陷。日志关键行是
`E sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101`——SD 卡**每次读**
的 DMA 缓冲（512B）都分配不出来 → 解码器从未真正启动 → `mp3_player` 按
"解码从未开始"判为 `MP3_STOP_DATA_CORRUPT` → 坏曲自动跳过下一首（随机模式
下即"跳到另一个队列"）。"先播一秒"是上一首的音频残留在 I2S/解码缓冲里。

**根因**：`lvgl_port.c` 的 `EXAMPLE_LVGL_BUF_HEIGHT = EXAMPLE_LCD_V_RES / 10`
→ 460×46×2B ≈ 42.3KB × 双缓冲 ≈ **84.6KB DMA**，把 DMA 池压到不足 3KB。

**DMA 池实测分布**（V_RES/20 那次测量，详见 `PSRAM_TASK_STACK.md` 第 4 节）：
启动 263KB → display 246KB → audio 233KB → SD 227KB → **LVGL 后 171KB** →
开机完成 **45KB**（boot_flow 的封面/JPEG 解码又吃掉 126KB）。⚠ 不能按"启动
瞬间还剩 263KB"估算，必须给开机流程留余量。

**修复**：`EXAMPLE_LVGL_BUF_HEIGHT` 改为 **`V_RES / 12`**（双缓冲 ≈ 70KB
DMA，稳态余量约 15KB，帧率接近原 30fps）。试过 V_RES/20（≈42KB，DMA 很
宽裕但帧率掉到约 20fps，用户反馈"原本满 30 帧现在掉到 20 帧左右"），故
取 /12 折中。

**顺带记录的失败尝试**：把绘制缓冲改成**非 DMA** 以省 DMA 池 → SPI 驱动为
每次传输分配 bounce 缓冲（`setup_dma_priv_buffer`）同样吃 DMA 池 →
`panel_io_spi_tx_color failed` / `Failed to allocate priv TX buffer` → 刷屏
阻塞 → 任务看门狗复位。**结论：绘制缓冲必须保持 `MALLOC_CAP_DMA`，只能调
高度**；调高度时必须同时看帧率与 `heap_caps_get_free_size(MALLOC_CAP_DMA)`。

**实测**（release 版，COM5）：开机不再有 `allocate_dma_buf` 失败，无坏曲
误判，随机模式开机直接进入随机队列；滚动/翻页流畅。

### 34.1 结论：内存已经不再是瓶颈

一句话：**"谁吃了 IRAM"查清了，"怎么还回来"也做完了。**
升级到 LVGL 9.4（+TTF 字体）之后"对象都搬去 PSRAM 了、可用内部 RAM 却不见涨"的谜团，
根因是 **ESP32-S3 上 IRAM 与内部 DRAM 是同一块 SRAM 的两个别名、二者零和**：
`.iram0.text` 里超出前 16 KB 的每一字节都直接从内部 DRAM 堆里扣（map 里的 `.dram0.dummy`），
所以"LVGL 代码进 IRAM"与"LVGL 对象放 PSRAM"在同一个池子里对冲。据此落地了
① 裁掉 6 种用不到的颜色格式（IRAM 省 57.5 KB）、② 路径B 把滚动热对象钉回内部 RAM、
③ 绘制缓冲早在 2026-09-10 就已回到 `V_RES/10` 并一直稳定运行。

| 指标 | 第 34 点提出时（2026-09，baseline） | 现在（2026-10-16 实测，路径B 后） |
|---|---|---|
| IRAM 代码（`.iram0.text`） | 166.4 KB（其中 LVGL blend 82.8 KB） | **108.9 KB**（LVGL blend 25.3 KB） |
| 内部 RAM 稳态空闲（`MEM: iram=`） | 23.5 KB | **38.8 KB** |
| 开机完成时内部 RAM 最大连续块 | **3.5 KB**（跌破项目 4 KB 底线） | **11.3 KB** |
| DMA 最大连续块 | 2.6 KB（连 SD 读的 512 B 都很紧张） | **11.3 KB** |
| LVGL 绘制缓冲 | 已回到 `V_RES/10` | **`V_RES/10`**（2 × 42 320 B ≈ 84.6 KB DMA） |

> ⚠ 口径提醒：`mem_monitor` 的 `iram=` 是 `heap_caps_get_free_size(MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT)`，
> 即**内部 DRAM 堆空闲**，不是指令 RAM；而 `idfc size` 报"IRAM 100% 已满"是 ESP32-S3 的正常现象
> （`.text/.vectors` 本就会用满），真正该盯的始终是**内部 RAM 余量与其最大连续块**
> （`IRAM_AUDIT_LVGL9.md` §1、§2）。
>
> ⚠ 上表"现在"一列的 38.8 KB / 11.3 KB 是**路径B 主动花掉 82.8 KB 钉滚动热对象之后**的余量
> （见 34.4 的方案② 是不钉对象的 82.3 KB / 58.8 KB）。两者都远高于 4 KB 底线，
> 项目选择用富余的内存换帧率——这正是"内存已经很充足"的体现。

### 34.2 账本：谁吃了 IRAM

| 项 | 量 | 说明 |
|---|---|---|
| LVGL blend 代码进 IRAM | **82.8 KB → 25.3 KB** | `LV_ATTRIBUTE_FAST_MEM_USE_IRAM=y` + v9 把 blend 按格式拆成多份并整份打属性；关掉 6 种用不到的颜色格式后连 RGB565/ARGB8888/RGB888 的文件本身也缩水近一半（每个 `lv_draw_sw_blend_to_XXX.c` 内含一份源格式分发表），`.flash.text` 同步 −60.2 KB（§10.1） |
| TTF 迁移的栈增量 | +~26 KB | LVGL 12→20 KB、deep_worker 8→12 KB、主任务 8→16 KB；**不能省**，是 FreeType 光栅化进栈的硬需求（`FontSystem.md` §5） |
| v9 对象搬进 PSRAM 的收益 | −65.5 KB | `app_ui_create` 段消耗 −105 KB → −39.6 KB；被上面两笔对冲，"没改善"是真的（§3） |
| 路径B 钉回内部 RAM 的热对象 | +82.8 KB 被占用 | 两个滚动列表页（占 UI 对象总量约 78%），换来快速滚动 +4 帧（§13） |

### 34.3 原验收标准逐条对照

| 原验收标准 | 结果 |
|---|---|
| 绘制缓冲回到 `V_RES/10`（≈83 KB DMA） | ✅ 已达成（2026-09-10 改回，`lvgl_port.c` 的 `EXAMPLE_LVGL_BUF_HEIGHT = V_RES/10` 至今未变） |
| DMA 稳态余量仍 ≥ 8~10 KB | ✅ 最大连续块 **11.3 KB**（分配判据），是一次 SD 读 512 B 的 20 倍以上 |
| SD 卡读写无 `allocate_dma_buf` 失败 | ✅ 路径B 落地后设备处于日常使用状态，未再报告该故障与"误判坏曲自动跳曲"（本次未重跑串口复测，服务器未启动；依据是落地后的连续正常使用） |
| `MALLOC_CAP_INTERNAL` 最大连续块 ≥ 4 KB | ✅ 开机完成时 **11.3 KB** |
| 列表滚动帧率回到 30fps | ⚠ **未严格达标**：路径B 把快速滚动从 11 → **15fps 量级**、慢速滚动 **20+fps**，但没有 30fps |

关于最后一条：**帧率上限已不再由内存决定**。§12.1 实测三个杠杆的排序是
「对象放哪（内部 RAM 21fps vs PSRAM 11fps）>> blend 放哪（11 vs 9）>> 字体方案（11 vs 12）」，
而路径B 已把滚动列表页的热对象全部钉进内部 RAM（§13.2 证明钉住量超过 ~83 KB 后收益归零）。
要继续提速方向在绘制管线 / 虚拟列表的重绑策略，不属于"内存优化"，因此**不再作为第 34 点的遗留项**。

### 34.4 四配置对照（最终决策依据，`IRAM_AUDIT_LVGL9.md` §10.3）

| 方案 | IRAM 代码 | 内部 RAM 稳态 | 开机后最大连续块 | DMA（开机完成） | blend 执行位置 | 帧率 |
|---|---|---|---|---|---|---|
| ① baseline：FAST_MEM=y + 全格式 | 166.4 KB | 23.5 KB | 3.5 KB | 2.7 KB | IRAM | 11 fps |
| ② FAST_MEM=y + 裁格式（**已采用**） | 108.9 KB | **82.3 KB** | 31.7 KB | 58.8 KB | **IRAM** | **11 fps** |
| ③ FAST_MEM=n + 全格式 | 83.6 KB | 106.7 KB | 31.7 KB | 83.4 KB | PSRAM | 9 fps |
| ④ FAST_MEM=n + 裁格式 | 83.6 KB | **106.3 KB** | 31.7 KB | 83.4 KB | PSRAM | 9 fps |

读法：**②↔④ 只差 24 KB 内部 RAM / 1 帧**，而 ② 是"性能零代价"方案（blend 仍全在 IRAM，
内部 RAM 同时从 23.5 KB 涨到 82.3 KB）；① 无论从哪个角度看都该淘汰。定稿采用 ②。

### 34.5 落地改动清单

  固件体积反而 **−62 KB**。

### 34.6 失败实验（已记档，勿重试）

- **把 LVGL 对象全部搬回内部 RAM**（`LV_USE_CUSTOM_MALLOC` → `LV_USE_CLIB_MALLOC`）：两次都失败。
  对象堆总量约 **88~90 KB**，而内部 RAM 的账算死了（总量 ≈231 KB = 静态段 68 KB + 绘制缓冲 84.6 KB +
  任务栈 ~60 KB + …），即使关掉 FAST_MEM 多出 83 KB 也不够。失败过程精确复现了
  「内部 RAM 见底 → SD 读 512 B 失败 → 误判坏曲 → 自动跳曲」这条经典故障链，
  可直接当故障复现手册用（§11）。
- **把钉住窗口放大到整个 `app_ui_create`**：钉住量 ×1.28，帧率**零收益**，
  DMA 最大连续块掉到 **208 B**（低于一次 SD 读所需的 512 B）→ 最终收敛为"只钉两个滚动列表页"（§13.2、§13.4）。

### 34.7 余下未做、且决定不做

- **P2：把音频静态缓冲搬到 PSRAM**（`read_buf` 16 KB + `silence_flush` 11.25 KB 等，合计约 40.2 KB）——
  既然内部 RAM 已有 38.8 KB 稳态 + 11.3 KB 连续块，收益不再必要，且要动解码热路径，**不做**。
- **P3：继续压缩绘制缓冲**（降到 `V_RES/20` 等）——那是拿帧率换内存，当前内存充足，**不做**；
  `lvgl_port.c` 里保留"若再现 `allocate_dma_buf` 失败/无故跳曲就退回 `/12`"的退路注释。
- **P4：零碎 IRAM 项**（newlib / SD SPI ISR / ringbuf，合计约 10 KB）——风险大于收益，**不做**。

## 35. ClickWheel 按钮浮在下拉控制中心之上 ✅ 已修复

**现象**：长列表页（目录/歌曲页）右下角的黄色 ClickWheel 速滑按钮，
在下拉控制中心展开后**浮在控制中心之上**（视觉穿帮），并且会抢走按钮
区域的触摸（它与面板底部"上拉关闭"把手区重叠）→ 面板右下角的上拉手势
被按钮吃掉。

**根因**：ClickWheel 创建在 `lv_layer_top()`（系统最顶层，`main_ui_create`
里创建），而下拉控制中心面板创建在 `lv_scr_act()` 上——顶层永远高于屏幕层，
与两者谁后创建无关。

**修复（按 Z 轴顺序，而非"打开时隐藏按钮"）**：把通知栏面板也挂到
`lv_layer_top()`（`notification_panel_create`）。`app_ui_create` 的顺序是
`main_ui_create()`（含 `click_wheel_create()`）→ `create_status_bar()` →
`notification_panel_create()` → `settings_menu_create()`，因此面板与按钮
**同层且创建更晚** → 面板天然绘制在按钮之上并接管其区域的触摸，
展开时自然遮挡，完全不需要隐藏按钮。

- 曾先实现"面板开合时调 `click_wheel_set_overlay()` 隐藏按钮"的版本，
  属于治标（需要跟踪拖拽/动画状态，还得为覆盖层来源分多个布尔量），
  已按用户意见改为上述 Z 轴方案并全部回退；
- ⚠ 顺序敏感：`notification_panel_create()` 必须在 `click_wheel_create()`
  之后调用（当前由 `app_ui_create` 保证），否则按钮会反过来盖住面板；
- Toast 为懒创建（首次弹提示时创建，晚于面板）→ 仍位于面板之上，
  面板展开时的提示（如"睡眠定时已开启"）照常可见；
- 设置菜单仍在 `lv_scr_act()` 上（低于顶层），所以它的
  `click_wheel_set_overlay(true/false)` 保留不变——它确实需要主动隐藏按钮。

**验证**（debug 版 COM12，2026-09-10）：开机日志确认创建顺序为
`click wheel created on top layer`(1251ms) → `Notification panel created`(1321ms)，
同在 `lv_layer_top()` 且面板更晚 → 面板必在按钮之上；随后实测面板展开/收起、
面板内点设置进入菜单、ClickWheel 画圈翻页（`rotate .. deg -> scroll ..` 日志）
均正常。视觉遮挡效果请以设备实际观感为准。

## 37. 再次修复状态栏/控制栏透明度 Bug ✅ 已修复

> 原记录见本文档第 15 点（当时判为"不修复"）。

**现象**（用户反馈的易触发路径）：在正在播放页点封面把标题栏/控制栏
（联动状态栏）隐藏后，**滑动页面再滑回播放页**（不松手拖出去又拖回来也算），
再点封面让栏复现时，**控制栏变成全透明的**（只剩按钮图标浮在封面上）。

**根因**：显隐与透明度由两条时机不同的路径分别设置——

- 透明度：滑动**开始**时（`np_on_scroll_begin`，为省带宽把栏改为不透明纯黑）；
- 强制显示：页码**变化**时（`main_tabs_sync` → `now_playing_force_show_ui`）。

于是"栏处于隐藏状态时开始滑动"这一场景下：`SCROLL_BEGIN` 把背景改成不透明，
滑动结束 `np_on_scroll_end` 又按 `s_ui_visible == false` 把背景渐变为
**全透明**，而栏仍是隐藏的 → 状态机停在"隐藏 + 全透明"；用户随后点封面
显示栏时只清了 `HIDDEN` 标志、没人恢复背景 → 栏"已显示但看不见"。

**修复**：`np_on_scroll_begin()` 里**先恢复显隐、再改透明度**——
`s_ui_visible == false` 时先 `np_set_ui_visible(true)`（恢复标题栏/控制栏
与顶部状态栏显示），紧接着才设不透明纯黑。这样"隐藏状态下滑动"的触发
场景被彻底消除（滑动一定从"栏可见"开始，滑动结束必然回到半透明）。

配套的两处状态一致性加固（都在 `ui/now_playing.c`）：

- `np_set_ui_visible()`：显隐与背景不透明度**一起**改——显示 → `NP_BARS_OPA`
  (191) 半透明，隐藏 → `LV_OPA_TRANSP`，不再出现"隐藏但留着半透明背景 /
  显示却带着全透明背景"的组合；
- `now_playing_force_show_ui()`：仅当栏**此前确实隐藏**时才补回半透明背景
  （用于程序化切页等路径）。⚠ 栏此前已显示时**不动**背景：该函数由
  `main_tabs_sync` 在 `VALUE_CHANGED` 时调用，而该事件早于惯性滚动动画
  结束，此时背景必须是滚动期间的不透明纯黑，否则惯性滚动中会退回 alpha 混合。

**验证**（debug 版 COM12，2026-09-10）：编译无新增警告、烧录后开机与翻页/
画圈日志正常。该 bug 属视觉现象，**请以设备实际观感确认**：隐藏栏 → 左右
滑动翻页（含拖出去又拖回）→ 返回播放页 → 点封面，栏应正常复现为半透明黑
而不是全透明；滑动期间仍保持不透明纯黑。

## 38. 下拉控制中心拉到一半后严重掉帧（面板离开"屏幕层"→ 被遮住的整屏内容每帧重绘）✅ 已修复

**现象**（用户反馈，release 版跨版本对比）：HEAD 编译的 release 固件下拉
控制中心，**拉到一半之后开始严重掉帧**；0.9.0.0 alpha 3 固件在同样深度的
下拉始终顺滑。

**定位**：alpha3（`6493537`）→ HEAD 之间**唯一**落在下拉刷屏路径上的改动，
就是第 35 点的修复——`notification_panel_create()` 把面板父对象从
`lv_scr_act()` 改成 `lv_layer_top()`（为了让控制中心盖住 ClickWheel 按钮）。
面板自身的逻辑/样式/定时器一行未改（绘制缓冲大小、堆毒化开关、release 的
调试项也都与 alpha3 一致，已逐项核对）。

**根因**：LVGL 8 每帧按绘制缓冲高度（`460×46×2B` → 每块 46 行）分块刷新，
每块先用 `lv_refr_get_top_obj()` 在**当前屏幕的子对象树里**查找"完全覆盖该
绘制块的不透明对象"，命中即跳过它下面的一切（`lv_refr.c:730`、
`lv_refr.c:805-838`），随后 `lv_refr.c:792-794` 再**无条件**重绘 top/sys 层：

- **alpha3**：面板在屏幕树内、背景不透明（`lv_obj.c:487-521` 的 COVER_CHECK
  返回 `COVER`）→ 每个块都命中面板 → 被它遮住的页面内容**一律不画**，
  每块只填一块纯黑 + 十来个控件；
- **HEAD**：面板挂在顶层、已不在屏幕树里 → 每个块的覆盖判定回落到 tabview →
  **每块把整屏内容画一遍**（默认停在正在播放页：460×460 封面图从 PSRAM 拷
  42KB/块、标题栏/控制栏两条 α=191 半透明黑的混合、中文字形），顶层再把
  面板画一遍 → 绘制量约 2~3 倍，且多出来的都是最贵的部分。

**为什么偏偏"一半"**：拖动时无效区域 = 屏幕 ∩ 面板矩形 = 第 0 行到面板底边
（露出高度 = 460 + y）。按 46 行切块：露出 ≤ 230 行 = 5 块，231 行 = 6 块
——**半屏正好是"5 块 → 6 块"的台阶**，越过台阶要整整多画一块（外加一次
42KB 的 SPI flush）；叠加"每块还要画页面内容"后单帧时间越过 33ms
（`CONFIG_LV_DISP_DEF_REFR_PERIOD=33`）→ 帧率腰斩（30 → 15~20fps），
体感就是"过了一半突然严重掉帧"而非缓慢变卡。alpha3 每块只有纯色面板，
多一块也远在预算内，所以完全无感。

⚠ 同一机制项目里早已踩过：`settings_menu_show()` 之所以要
`main_ui_set_visible(false)`，正是因为菜单滚动时底层播放页的封面大图
仍在参与重绘。

**修复**：把 ClickWheel 按钮与其 12 个指示圆点改挂 `lv_scr_act()`（屏幕层），
面板也改回 `lv_scr_act()` —— **同层、Z 序由创建顺序保证**（`app_ui_create`：
`main_ui_create()`（内含按钮）→ `create_status_bar()` →

## 40. 跑马灯动画统一节奏（FUTURE_PLAN 第 36 点）✅ 已完成

**需求**（用户）：全项目的跑马灯（超长文本滚动）统一成"先停顿 → 只滚动 3 轮 →

2. 模板里**只读** `act_time`（起始延迟）与 `repeat_delay`（轮间停顿），

3. `repeat_count` 被 lv_label **写死为无限**

③ 200ms 守护定时器兜底：LVGL 在文本/尺寸/样式变化时会重建动画（轮数又变回无限），
按 `anim->user_data` 标记判断"没接管过"就补一次。

**参数**（`global_style.h` 顶部宏，按用户要求**不放 Kconfig**）：轮数 3、轮间停顿 1000ms、

**验证**（debug 版，COM12，2026-09）：编译无警告、二进制与实测固件一致；

## 41. ClickWheel 行对齐步进：只向列表输出行高的整数倍 ✅ 已完成

**需求**（用户）：ClickWheel 内部照旧按角度/像素做连续计算，但**输出给列表的
滚动量只取行高（itemHeight）的整数倍**，内部不足一行的量自行累加。这样
`virtual_list` 的行槽在屏幕上位置不变，转动时是"内容一格一格换"的阶梯式翻行
（纯视觉效果，数据不变）。**补充需求（同日）**：步进必须是**相对列表当前位置**
的——"滚动到那里，就按照那个样子一格格跳，保持现有项目的位置"；滚到最底下继续滚
要**按最后一项对齐**（而不是被拽去与第一项对齐）。

**实现**：

- `main/core/ui/virtual_list.{h,c}`：新增只读访问器
  `lv_coord_t virtual_list_get_item_height(lv_obj_t *list)`（NULL/非法返回 0），
  供外部按整行驱动滚动；ClickWheel 因此不必知道列表内部结构；
- `main/core/ui/click_wheel.c`：
  - 新增状态 `s_cur_item_h`（行高，`cw_target()` 时随滚动目标一起锁定）与
    `s_scroll_acc`（float 累加器，只存"不足一行的余量"，天然有界 ≤ 一行）；
  - `cw_scroll_by_deg()` 重写为"累加 → 取整行 → 扣余量 → 输出整数倍"四步：
    `s_scroll_acc += px`；`rows = (long)(s_scroll_acc / item_h)`（朝 0 截断）；
    `s_scroll_acc -= rows * item_h`；`lv_obj_scroll_by_bounded(list, 0, rows*item_h)`；
  - 删掉旧的"不足 1px 直接丢弃"——小角度转动不再丢量，而是留在累加器里，
    转够一行时一次性走一行；
  - **边界交给列表自己 clamp**：不做 `avail/max_rows` 预钳制、也不清累加器，
    越界量由 `lv_obj_scroll_by_bounded()` 丢弃 → 滚到底正好停在**最后一项贴底**
    （顶部停在 0 = 第一项贴顶）；余量有界，反向转动最多"还"一行就立刻响应；
  - 行高取不到（非 virtual_list）时退化为旧的按像素滚动；`CW_MAX_STEP_PX`
    单帧钳制保留（一帧最多跨 `800/item_h` = 14 行）。
- ⚠ **中途返工**：第一版在"首次转动"时把列表吸附到 `round(scroll_y/item_h)*item_h`
  （即按**第一项**建立的整行网格，`cw_snap_to_row()` + `s_row_aligned`），
  用户实测后否掉——那会把列表强行拽到与第一项对齐的网格上，破坏"保持现有位置"。
  **已整体删除，不要加回来**。连带变化：先前"位置恒为行高整数倍"的说法不再成立，
  改为"**输出恒为行高整数倍** → 行槽屏幕坐标的小数相位全程不变"。

**代价/边界**：不再平滑跟手（改为阶梯式，一帧可跨多行）——这是需求本身的手感。

**附带收益（意外发现，用户实测报告）**：格进式把"可见位移"与"帧时序"解耦了，
于是 ① **位移精度变成帧率无关**（格数由角度差算出，掉帧不再累积成"少滚一段"，
平滑滚动则会）；② 快速滚动时原本的不稳定帧率**在体感上不再表现为卡顿**——
帧变慢时平滑滚动是一次突进（被眼睛读作一顿），按格滚动只表现为"这一下多跳了几格"，
而它本来就该是不均匀的离散节奏。即抖动的表现形式从"画面一顿"降级为"节奏稍慢"，
是更宽容的失败模式。⚠ 只改观感、不省绘制开销（每帧仍是一次列表区整块重绘），
底层帧率问题不能拿它当遮羞布（实测画圈期间 Core0 约 92~97%、空闲 3~6%）。
已同步进 `CLICK_WHEEL_USAGE.md` 2.3.2 与 `click_wheel.{h,c}` 注释。

**同步更新**：`click_wheel.h` 头部说明（含"行对齐步进 / 相对当前位置 / 边界 clamp"
要点与角度换算公式）、`CLICK_WHEEL_USAGE.md` 1 节与 2.3 节（重写为相对步进 +
明确"不要加回吸附"+ 新增 2.3.1 节说明与虚拟列表的配合）、2.5 节与踩坑 1 的过期描述
（"按钮/圆点挂 `lv_layer_top()`"→ 实际为 `lv_scr_act()` 屏幕层，源码早已改，
文档此处为历史残留）。

**验证**：编译无警告；串口日志格式改为
`rotate %.0f deg -> %ld row(s) (%d px, scroll_y=%d)`，可核对"输出像素 = 行高整数倍"。
**设备实测（COM5，2026-09，加吸附的旧版本）**：所有 `px` 与 `scroll_y` 均为 56 的

## 42. ClickWheel 大改：条目数驱动的圈数模型 +「虚拟 ClickWheel 选项」子菜单（开关/方向/速度三档）✅ 已完成

> ⚠ 本条**合并**了本次会话对 ClickWheel 的全部改动（原分 #42/#43/#44 三条，
> 2026-09-11 按用户要求合并为一条）：① 圈数模型；② 设置子菜单；③ 速度三档。
> 涉及文件：`core/ui/click_wheel.{h,c}`、`core/storage/config_store.{h,c}`、

### 42.1 需求（用户，2026-09-11，按提出顺序）

1. **圈数由条目数决定**（用户数学建模），取代原先由 `CW_TURN_RATIO` 固定的
   "5 圈到底"：

3. **速度三档、点击循环**：普通（不计算）×1.00 / 快速 ×0.75 / 极速 ×0.50

4. **入口行文案**：标题「虚拟 ClickWheel 选项」、**不显示右侧开/关状态**

### 42.2 实现

**(1) `core/ui/click_wheel.{h,c}` —— 模型与三个运行期开关**

- 新增 `cw_turns_for_count(count)`（`ln(x)/ln(1.618) − 7` 后钳制）：只在锁定
  滚动目标时算一次（按下瞬间 / 换列表），转圈期间条目数不变，两次 `logf` 的
  开销可忽略；
- 状态：`s_cur_turns`（有效圈数）、`s_reverse`（方向）、`s_speed`（档位），与
  `s_cur_list` / `s_cur_count` / `s_cur_item_h` 一起由 `cw_target()` 锁定
  （防画圈途中切页/换列表）；
- 距离基准由"内容总高度"改为**可滚动行程**：
  `range = scroll_top + scroll_bottom`（恒等于 `内容总高度 − 视口高度`，与当前
  滚动位置无关）。这才是"滚完整个列表"要走的行程，转满 y 圈正好停到最后一项
  贴底；`range <= 0`（内容不足一屏）直接返回（取代原 `content_h <= view_h` 判据）；
- 换算 `px_per_deg = range / (turns × 360)`（原 `content_h × 0.2 / 360`），其中
  `turns = cw_effective_turns() = cw_turns_for_count() × CW_SPEED_FACTOR[speed]`；
  行对齐步进、`lv_obj_scroll_by_bounded` 边界 clamp 全部不变；
- 单帧钳制由固定 `CW_MAX_STEP_PX = 800` 改为**按角度钳制**
  `CW_MAX_STEP_DEG = 90°`（= 1/4 圈，随行程/圈数一起标定）：固定像素上限对
  73 条（每圈约 34 行）是半个圈，对 10000 条却只是几十分之一圈，长列表快速
  画圈时单帧滚动量会被削顶（旧注释已警告过）；按角度钳制后各规模保护强度一致，
  正常转动（10~40°/帧）不受影响；
- 方向：`dir_sign = s_reverse ? +1 : -1`（每帧换算处取符号，切页/换列表无需
  重算）；接口 `click_wheel_set_reverse(bool)`；
- 档位：宏 `CLICK_WHEEL_SPEED_NORMAL/FAST/TURBO/COUNT` + 系数表
  `CW_SPEED_FACTOR[3] = { 1.00f, 0.75f, 0.50f }`（取代原单一宏
  `CW_FAST_TURN_FACTOR`）+ 日志名表 `CW_SPEED_NAME[3] = {"normal","fast",
  "turbo"}`；接口 `click_wheel_set_speed(uint8_t)`（越界钳到普通），切换时调
  一次 `cw_target()` 让当前列表立刻套用新系数；
- 日志：列表登记 `tab %u list set: items=%u (%.2f turns to end, %s)`；档位切换
  `click wheel speed: fast (x0.75 -> 4.75 turns for 611 items)`（当前页面没有
  绑定列表时只报档位 `(x0.75, no list bound)`，避免误导性的
  "1.00 turns for 0 items"）。

**(2) `core/storage/config_store.{h,c}` —— 三项 NVS 配置**

| `clkwheel_rev` | `s_cw_reverse` | 正常/反转 | 正常 | 正常 = 顺时针向下滚；反转 = 顺时针向上滚 |

### 45.4 `idfc menuconfig`：查询配置项（2026-09-23 完成，由另一个 Agent 实现）

需求就是清单里那条原话：「build 目录下有个 json 记录了所有可用的 menuconfig 设置项，且其中包含详细的描述说明」。
本轮先在 `tempdir/kconfig_menus/`（**未入库，tempdir 被 .gitignore 忽略**）做了一层解析类原型并测通
**69 条断言**（结构不变量 / 已知事实 / 边界容错 / 性能），随后正式实现进 IDFClientCLI 仓库：
`Core/Kconfig/KconfigMenus.cs`、`Core/Kconfig/KconfigValues.cs`、
`Client/CustomCommands/MenuconfigCommand.cs`（命名空间改为 `IDFClientCLI.Core.Kconfig`，解析逻辑与原型一致）。

命令形态（**纯客户端**：只读 `build/<variant>/config/` 下的两个 json，不经过 IDF 服务器、不触发构建）：

| 子命令 | 行为 |
|---|---|
| `menuconfig search "关键词1 关键词2" [--page N]` | 多关键词 **AND** 检索：关键词按**字面**匹配（`Regex.Escape`）、不区分大小写，且必须落在**同一个字段**（`id` / 符号名 / 标题 / 说明）里；每页 20 条，超出时打印匹配总数与翻页提示 |
| `menuconfig desc <名称>` | 单项详情：名称 / 类型 / 取值范围 / 当前值 / 依赖 / 所在菜单路径 / 说明全文。名称可带可不带 `CONFIG_` 前缀、大小写不限，也接受菜单节点的小写 id（如 `build-type-application-build-type`） |

实现方在边界行为上处理到位、值得留档的两点（均为实现方自己的实测结论）：

- **`\A` 锚点防正则退化**：多关键词用零宽前瞻串联（`\A(?=[\s\S]*K1)(?=[\s\S]*K2)`）。少了开头的 `\A`，
  前瞻失败会让引擎从**每一个字符位置**重试、每次都线性扫到尾，实现方实测把检索从 ~0.3s 拖到 ~3.3s（O(n²)）；
  用 `[\s\S]` 而不是 `.`，才能跨过 help 里那 1298 条含换行的说明。
- **`-t` 会把自己的位置置 null**，所以 `menuconfig desc -t debug X` 不能用 `PopFirstArg` 取名称（已改为取"第一个非 null 参数"）。

数据规模与性能（实测 debug 构建）：`kconfig_menus.json` **2.6MB / 4079 节点**，
`sdkconfig.json` **1730 个键**；解析约 52~58ms、全字段扫描约 1ms —— **每次命令现读现解析即可，无需缓存**。

退出码：`0` 成功；`1` = 参数错误 / 缺 json（提示先构建）/ 没有匹配项 / 页码越界。
⚠ 它依赖**该构建类型至少成功构建过一次**（两个 json 由 ESP-IDF 在配置阶段生成）。
其余边界行为由实现方单独测过，本次未重复测试。

## 49. 睡眠定时器自动开启 bug + 睡眠定时与配置槽位解耦（从 legacy_s3 移植）✅ 已完成（2026-11-14）

> 来源：`FUTURE_PLAN.md` 第 49 点（`legacy_s3` commit `4eb04c6`）。
> 数据模型与运行时应用的完整说明见 **`CONFIG_SLOTS.md` §九**。

**根因**：睡眠定时时长 `sleep_default_min` 被当成"配置槽位字段"，于是两条

1. `main/main.c`：删掉 else 分支，只保留 `sleep_timer_boot_autostart_min() > 0`
   时启动；开关关闭时打 `boot: sleep timer off (开机默认开启已关闭)`；
2. `core/storage/config_slots.c`：切槽位**完全不碰**睡眠定时（不 set 也不 cancel），

**改完的语义**：睡眠定时只由三处改变——设置页睡眠格子、通知栏睡眠开关、

## 51. 虚拟列表滚动性能：重绑策略之后的下一步 ⏸ 暂不实现（2026-11-14 关闭）

> **⏸ 2026-11-14 决策：暂不实现（整条 51 含 51.1 一并关闭）**。理由：
> S3 有旧版 IRAM 兜底（`legacy_s3` 分支保留原方案），S31 本身性能足够
> （当前列表快速滚动 24~36 fps、慢速滚动 20+ fps，用户确认可接受），
> 不再继续投入虚拟列表滚动性能优化。以下调查/实验记录仅作留档；
> §51.1 的 `listview_perf_improvement` 实验分支也不合并回主干。

**来源**：`DONE_PLANS` 第 34 点的尾巴（`IRAM_AUDIT_LVGL9.md` §13.4 第 2 条）
——「若要继续提速，方向在别处（绘制管线、虚拟列表的重绑策略等），不是继续钉对象」。
当前实测基线：列表快速滚动 **15 fps**、慢速 **20+ fps**，30 fps 目标未达成。

**已完成的部分（2026-10-16）**：**可行性调查**，报告见
**`ideas_and_exps/VIRTUAL_LIST_REBIND_STRATEGY.md`**。核心结论三条：

1. **重绑策略本身已接近最优**（每跨一行只重绑 1 行，O(1)/行），继续抠"重绑"收益小；
   只剩"图标文本/颜色无谓重设"这点单价冗余（`lv_label_set_text` 无条件
   free+malloc+度量，`lv_obj_set_local_style_prop` 无相同值短路）。
2. **真正的天花板是 LVGL 的滚动语义**：`lv_obj_scroll_by_raw()` 在 `lv_obj_scroll.c:413`
   无条件 `lv_obj_invalidate(obj)` → **每帧必然重绘整个列表区**（≈180K 像素、
   ≈110 个汉字字形）。要把 dirty 降成"一条窄带"，唯一办法是**不用 LVGL 原生滚动**
   （方案 S1 视口槽位制 + 自管滚动），代价是触摸滚动只能按整行吸附
   ——**该方案已因手感问题出局，见下方「已决策」**。
3. **fps 与单帧耗时成反比，没有"跨门槛翻倍"的巧取空间**：项目开了
   `LV_USE_PERF_MONITOR`，刷新定时器在渲染前**不被暂停**（`lv_refr.c:361` 的
   `#if !LV_USE_PERF_MONITOR lv_timer_pause(tmr)`），加上 `lv_timer.c:322` 先写
   `last_run` 再调回调 ⇒ 渲染一结束就立刻开下一帧，`fps ≈ 1000 / 单帧 ms`。
   所以 **15 fps ⇒ 单帧 ≈65 ms，30 fps ⇒ 必须砍到 32 ms（腰斩）**，
   收益线性可外推，验收口径必须是**单帧毫秒数**而不是 fps。
   （⚠ 调查初稿曾误判为"33 ms 节拍跳档"，已在报告 §2.1 更正。）

**已决策（2026-10-16，用户）**：**方案 S1（视口槽位制 + 自管滚动）出局**——
它的前提是触摸滚动只能按整行吸附、失去连续跟手，用户不接受。
⇒ **"把整块 dirty 降成一条窄带"这条结构性捷径已关闭**，
只剩"降低单帧成本"一条路。另一个推论：慢速滚动实测已有 48 ms 底座，
**即使重绑成本降到 0 也只能到 20 fps**，不砍底座就一定到不了 30 fps。

**待做（按顺序）**：

- 第 0 阶段（**一切判断的前提**，用户当前选择"暂不动固件"故推迟）：
  加"单帧耗时直方图"埋点（E1）+ 三段对照（E2：正常重绑 / 跳过重绑 / 静止，
  用 `lv_timer` 自动滚动），**1 次烧录、不改行为**。产出单帧毫秒数、重绑占比、
  以及"空帧率"（用来分辨"快速比慢速慢 15 ms"是重绑单价高、还是慢速时混了空帧）。
- 第 1 阶段（便宜、不改架构）：F2（`LV_FREETYPE_CACHE_FT_GLYPH_CNT` 1024→4096）
  + F4（重绑去冗余：图标 `strcmp`、颜色先比较再设）。
  单帧明显下降 ⇒ 进第 2 阶段；几乎不动 ⇒ 底座是"物理必需的绘制"，
  **要果断停手，不要零敲碎打**。
- 第 2 阶段（按 E1/E2 归因二选一）：底座是对象/样式/管线 → F5（去行容器）
  + S2（行位图缓存）；底座是字形 blend 像素量 → S3（Xtensa SIMD blend，
  当前 `LV_DRAW_SW_ASM_NONE`，需走 `LV_DRAW_SW_ASM_CUSTOM`）。
- 第 3 阶段：F1（`REFR_PERIOD` 33→16）——**只在单帧已 <33 ms 后做**，否则零收益。

**长期候选（用户提出并修订，已评估，未实施）——S4：自己接管列表绘制**

用户设想（借鉴 NightPlayer 前身 FantasticMusicPlayer 的思路）：既然列表每帧都要整块重绘，
不如自己接管列表的绘制。**同日用户修订为**：「**不是**一次性绘制整个列表，而是
**只提供一个和视口大小一样的缓冲区，按照位置只绘制需要的项目**；列表的**坐标和惯性
计算之类的东西可以放在 IRAM 里**，同时**缓存小图标**。」
报告 §5.2.1 已按修订版重写完整评估，要点：

- **推荐实现形式**：**LVGL 的自定义绘制回调**（`LV_EVENT_DRAW_MAIN` +
  `lv_event_get_layer()` + `lv_draw_label()` / `lv_draw_image()`，全部是 9.4 公开 API），
  直接画进 LVGL 当前的绘制缓冲。
  ⚠ 这条很关键：若另建一块 PSRAM 的"视口缓冲"，每帧要多搬运 360 KB
  （**额外 7~9 ms，是现在没有的开销**），正好抵消掉收益。
- **砍掉什么**：每帧被 LVGL 遍历 / 派发事件 / 解析样式的对象从 **19 个降到 1 个**
  （→ 消掉 H3 对象/样式开销与 H5 管线开销）；样式链完全不解析（`dsc` 里直接填 font/color）。
- **没砍掉什么**：**每帧仍要画 ≈126 个汉字**（H1 重复光栅化、H2 mask blend 照旧）。
  这与"长条 surface + 跨帧复用"是本质区别——修订版用"实现简单"换掉了"字形零重画"。
- **手感**：完全保留 LVGL 原生滚动 / 惯性 / 滚动条（不需要 S1 的自管滚动，不触碰整行吸附）。
- **用户要求的两项**：① 坐标 / 惯性 / 行索引等热数据用
  `heap_caps_malloc(MALLOC_CAP_INTERNAL)` 显式放内部 RAM——这套方案下 LVGL 对象只剩 1 个，
  **路径B 的"钉 19 个行槽对象"机制不再需要，天然被取代**；
  ② 图标预渲染成 4 张小位图（`LV_SYMBOL_AUDIO` / `_DIRECTORY` / `_LIST` / `_SD_CARD`，
  20×20×2B×4 ≈ 3.2 KB，可整体放内部 RAM），绘制时 `lv_draw_image` 直接 blit，不再走字形路径。
- **代价**：**跑马灯要自己按 offset 实现**（最大工作量，含复刻 `global_style` 的
  "起始延迟 / 3 轮 / 轮间停顿"节奏）；文本宽度要自己调 `lv_text_get_size_attributes()`
  （这一项仍走 FreeType 度量，属 H1 残余）；点击命中改为按 y 坐标算行号；按下黄底自己画。
  切歌高亮反而变简单——draw 时按当前曲目判断即可，不再需要 `virtual_list_refresh()`
  重绑全部可见行。
- ⚠ **实施前仍要先做第 0 阶段测量**：它砍的是 H3/H5、不砍 H1/H2，
  所以"值不值得写"完全取决于底座归因——底座若是对象/样式开销 → 它能拿大头；
  若是字形渲染 → 收益有限，只能上 SIMD（S3）或接受每帧重画。

**⛔ 已严正否决：长条 / 跨帧复用的离屏内容缓存（即 S4 的最初设想）**

2026-10-16 用户：「长条方案应该严正否决，**因为存在单条 1000+ 的列表，长条必然会爆炸**」。
理由两条：

1. **产品约束**：本项目存在**单条 1000+ 项**的列表（大曲库、根目录）。长条要真正兑现
   "滚动时不重画字形"的价值，就得缓存**足以覆盖滚动范围**的内容 → 必然按 `item_count`
   分配 → 1000+ 行必然爆炸。
2. **技术印证**：若把它缩成固定窗口（初稿设想 12 行 / ≈618 KB PSRAM），它其实**退化**了
   ——ClickWheel 行对齐步进下单帧最多跨 **14 行**（`CW_MAX_STEP_PX=800 / item_h 56`），
   会直接冲垮 12 行窗口并触发"基准跳跃 + 整块重画"，于是又回到"每帧重画大部分行"，
   与视口重绘（修订版 S4）没有实质差别，却白背一套状态机。
   ⇒ **长条在本项目列表规模上没有存在价值，以后不要再评估。**

由此提炼出**约束四（报告 §2.6）：任何方案的资源占用都必须与 `item_count` 无关（O(1)）**。
✅ **已逐行核对：当前 `virtual_list` 满足这条**——所有分配都基于 `row_count`
（= 可见数 + 2 = 9），`item_count` 只参与边界判断和占位高度这一个标量。
**这是本项目虚拟列表最有价值的既有设计，任何改造（含 S4）都必须原样保持。**

**体感观测（2026-10-16，用户）**：「帧率忽高忽低，单帧时间有剧烈波动，实际体验较卡；
能忍，但希望改善。」→ 已记录为报告 §2.5。**"波动"比"均值低"更容易被读成卡顿**，
候选来源见该节；其中最值得先查的是 **Core1 争抢 PSRAM 带宽**（MP3 解码持续读写 PSRAM，
封面解码是突发大流量）——若成立，则第 0 阶段的测量必须**固定在同一个播放状态下**做，
否则数据不可比（也可能正是"快速 15 / 慢速 20+"这组历史数据本身不稳的原因）。

**当前状态（2026-10-16 用户决策）**：**保持现状，不做实施。**
本条只登记调查结论、方案清单与 S4 这个长期候选，等有需要时再从第 0 阶段往下走。

**明确不建议**（避免重复劳动）：**长条 / 跨帧复用的离屏内容缓存（见上，已严正否决）**、
继续加大对象钉住窗口（§13.2 已证明 83 KB 后收益归零）、
关闭 `LV_ATTRIBUTE_FAST_MEM_USE_IRAM`、把字形位图整体钉进内部 RAM、缩小绘制缓冲。

**做了什么**：把"§1 的核心结论"直接实施了一遍 —— 自己维护一块视口大小的 RGB565 画布

| 项 | 收益 | 记录位置 |
|---|---|---|
| LVGL tick 改 `lv_tick_set_cb()` 读硬件时间 | 修掉**整屏定格**的真 bug（IDF 6.1 esp_timer 任务派发通道丢闹钟）+ 省 500 次/秒中断 | `DISPLAY_FREEZE_TRIAGE.md` |

**试过但回退的（重要，别再走一遍）**：**QSPI 像素时钟 40 → 80 MHz**。
在实验分支上它把 render 从 27 → 24 ms（所有界面受益），但在**回灌主干后的连续实机上
暴露了"偶发 1px 纯黑竖线"残留**：被局部重绘的区域左边缘多出一条贯穿该区域高度的黑线，

都有。**判定方法（已实测确认）**：同一份固件只把 `AMOLED_QSPI_MAX_PCLK` 退回 40 MHz，
全部黑线立刻消失；把整份改动用 `git stash` 退回干净 master 也能复现"无黑线"。
⇒ 结论是**这块屏在本机走线上 80 MHz 处于传输时序边际**，为 3 ms render 不值得。
排查"画面残留/黑线"类问题，第一步先把 QSPI 退回 40 MHz 做对照。详见 AGENTS.md 的 QSPI 条目。

**仍在分支上、未回灌的**：`core/ui/vlist_canvas.c/.h`、`playlist_page.c` 的画布接入、

**本轮产生的新结论（替代/补充本条第 0 阶段的目的）**：

1. **瓶颈归因已经完成**（等价于原第 0 阶段）：滚动帧 `handle ≈ 43 ms` 拆开是
   `render 23 ms`（对象树遍历 + 画像素 17.5 ms + 字节交换/提交 5.5 ms）+ `timer 20 ms`，
   而 **约 34 ms 是"重画整个视口"这个物理必需项**。所以 30 fps（单帧 32 ms）在不改变
   "每帧整屏重绘"的前提下**不可能达成**——这与本条第 3 条结论一致，且已从"推断"变成"实测"。
2. **已证否、不要再试**（每条都有实测依据，详见 VLIST_CANVAS §4.6 与 §5.1）：
   只失效"新露出的那条带"（画面是错的，面板无显存滚动）、自己写 RGB565 字节交换
   （慢 30%，LVGL 那份在 IRAM）、滚动后催 `lv_refr_now()`（blit 量翻倍、更差）、
   把卡片整块圆角（掩码路径没那么贵，重复背景层才是大头）、
   **QSPI 80 MHz（会残留 1px 黑竖线，见上"试过但回退的"）**。
3. **`lv_draw_label` 的适用边界**：在**事件上下文**（非刷新循环内）同步渲染时，
   它会经 `lv_draw_dispatch_wait_for_request()` 卡到下一次刷新（33 ms）且任务可能被丢弃
   （文字**消失**）。要往自己的内存上画字必须逐字形混合
   （`lv_font_get_glyph_bitmap` + 手动 alpha blend + `lv_font_glyph_release_draw_data`），
   且 FreeType 会忽略传入的 `draw_buf`。
4. **仍未做的下一步**（按性价比，都在分支基础上继续）：减少绘制块数量（8 → 4 块，
   要动绘制缓冲与单/双缓冲权衡）、让列表区只剩一次整块填充、
   用 `lv_obj_scroll_by_raw()` 绕开 `lv_obj_add_state/remove_state(SCROLLED)` 的样式比对。

## 53. 蓝牙设置页滚动只有十几 fps（不透明全屏页挂在 lv_layer_top）✅ 已完成（2026-11-15，帧率待真机复核）

**现象**（用户反馈）：设置菜单 → 蓝牙，滚那个 `lv_menu` 页面只有十几 fps，与设置菜单
本身差一大截。怀疑"多盖了几层 / 不在主 UI 那一层"。

**根因**（与第 38 点同一机制）：`ui/bt_settings.c` 把整页（全屏不透明黑底 + `lv_menu`）
挂在 `lv_layer_top()`，同时设置菜单保留在下层。LVGL 9 的
`lv_refr_area_part()` 只对**当前屏幕**的子对象树做覆盖判定
（`lv_refr_get_top_obj()`，`lv_refr.c:1033`），top/sys 层随后**无条件**重画
（`lv_refr.c:1064-1066`）。于是每个绘制块都要：
① 把被蓝牙页完全盖住的设置菜单整页重画一遍 → ② 再画顶层蓝牙页。
绘制量约 2 倍，且多出来的是"深灰卡片 + 中文位图字形"这类最贵的部分 ⇒ 十几 fps。

**修复**（`ui/bt_settings.c`）：
- 页面父对象 `lv_layer_top()` → `lv_scr_act()`（屏幕层，与设置菜单/主界面同图层树）。
  全屏不透明背景 `s_bg` 成为覆盖对象，下层被覆盖判定跳过；
- 打开时 `overlay_enter()`：若设置菜单可见则先 `settings_menu_hide()`，再
  `main_ui_set_visible(false)` + `click_wheel_set_overlay(true)`——下层对象被隐藏，
  连"是否覆盖"都不用算（用户要求"打开蓝牙后后面的设置页面可以关掉"）；
- 关闭时 `overlay_leave()`：按来源恢复（设置菜单进来 → `settings_menu_show()`；
  控制中心快速面板进来 → 恢复主界面 + ClickWheel）；
- 每次 `show` 都 `lv_obj_move_foreground(s_bg)`：设置菜单外壳是懒加载的，可能在
  蓝牙页创建之后才建（那样它会排在后面），必须每次置顶。

**顺带把全部分层盘点了一遍**（规则写进 `main_ui.c` 的"覆盖层图层规则"注释）：

| 覆盖层 | 原层级 | 是否全屏不透明 | 处理 |
|---|---|---|---|
| 设置菜单 / 下拉控制中心 / 开机流程 / 关机提示 | 屏幕层 | 是 | 本来就对（第 38 点修的） |
| **蓝牙设置页** | `lv_layer_top` | 是 | **改屏幕层**（本条） |
| **WiFi 对时进度界面** | `lv_layer_top` | 是 | **改屏幕层**（`time_sync_ui.c`；对时固件里屏幕是空的，影响小，主要防以后复用踩坑） |
| 蓝牙快速面板 / EQ 选择 / 日期时间滚轮 / 对时确认框 | `lv_layer_top` | **否**（半透明遮罩+卡片） | **保持顶层**：遮罩必须叠在下层之上才有效果；而半透明父对象会让 `COVER_CHECK` 返回 `NOT_COVER`，放进屏幕树会被"跳过父对象、只画不透明子对象"的优化吃掉 → 调暗丢失 |
| Toast | `lv_layer_top` | 小卡片 | 保持（必须压一切，面积很小） |

> 结论（写代码时照此判断）：**全屏且不透明** → 屏幕层 + `main_ui_set_visible(false)`；
> **半透明遮罩/小弹窗** → 只能 `lv_layer_top()`。

**顺带修掉的返回键 bug（2026-11-15 用户反馈）**：在主视图点左上角返回键时，
返回按钮消失、页面不关闭。

- **根因**：`lv_menu_set_page()` 对**同一页面不去重**，每调用一次就 `cur_depth++`。
  本页在 `ensure_created()` 与每次 `bt_settings_show()`、以及"扫描页选设备/删除设备
  回主视图"等路径里反复 `lv_menu_set_page(s_page_main)`，于是主视图上的 `cur_depth`
  涨到 2、3… ⇒ `lv_menu` 认为"在子页"；而 `lv_menu_back_button_is_root()` 用的是
  点击前的 `prev_depth <= 1` 判定根页面 ⇒ 返回键点击被 `lv_menu` 自己的回调接管：
  它弹掉历史、`cur_depth` 落到 1 并**把返回键隐藏**（主视图默认不显示根返回键），
  我们的回调又因"不是根"而不关闭本页。
- **修法**：① `lv_menu_set_mode_root_back_button(ENABLED)`，主视图也显示返回键；
  ② 新增 `menu_goto_main()`：切主视图统一 `lv_menu_clear_history()` + `set_page()`，
  保证主视图上 `cur_depth` 恒为 1（子页面用普通 `set_page`，`cur_depth=2`，返回键
  由 lv_menu 退回主视图）；③ 所有"回主视图"的调用点（show / 扫描页选设备 /
  设备删除 / 设备已不存在）都改用 `menu_goto_main()`。与 `settings_menu_show()`
  的既有做法一致——它正是靠"已在根页面就不重复 set_page"避开同一个坑。

> 结论：**`lv_menu_set_page` 不是幂等的**，任何"反复回到同一页面"的代码都要
> 先判当前页（或清历史后重设），否则 `cur_depth` 会虚高、根返回键判定失效。

**验证**：debug 构建通过、烧录后开机日志正常（`App started`）；蓝牙页滚动帧率
与"从设置菜单进入/返回、从快速面板进入/返回、主视图返回键关闭"待真机实测确认。

## 54. 蓝牙设备详情页状态变化后滚动跳回顶部（改增量更新）+ UI 文案精简 ✅ 已完成（2026-11-15，待真机复核）

**现象**（用户反馈）：设备详情页里连接/断开、切换 EQ、甚至点「删除设备」，
整个页面都会滚回顶部；点删除还会因为重建把"再次点击确认删除"的状态行刷走，
得重新滚到底再点一次。

**根因**：`ui/bt_settings.c` 的 `refresh_timer_cb` 用 `state_hash()` 判断"有变化"
后直接 `build_device()/build_main()/build_scan()` —— `lv_obj_clean(page)` + 重建
全部行。清空瞬间页面内容高度归零，滚动位置被钳到 0，重建后自然停在顶部；
`state_hash` 把连接状态、音量、EQ、`s_delete_armed` 等全算了进去，于是**任何**
状态变化都会触发整页重建。

**修法（增量更新）**：
- 三个页面的内容只在首次打开时创建一次；`refresh_timer_cb` 只调
  `update_main()/update_device()/update_scan()`；
- 新增 `set_label_text / set_label_color / set_obj_hidden` 三个"值没变就直接
  返回"的辅助函数 → 每 500ms 轮询也几乎零开销、不产生多余重绘；
- 设备行与扫描结果行**预建固定数量**（5 / `SCAN_ROWS_MAX=16`），只切换显隐：
  行下标天然等于 bt_store 槽位 / 扫描结果下标，删除设备后前移也不需要重建；
- 删除设备的两段确认只改本行标题（`s_delete_armed`），不再重建；
- 进入设备详情时显式 `lv_obj_scroll_to_y(s_page_dev, 0, ...)`（换设备才回顶部），
  页面内的状态更新则完全不碰滚动位置；
- `state_hash()` 删除（不再需要）。

**UI 文案（用户要求）**：
- 「安静模式」在 UI 上改名 **「睡眠免打扰」**（Toast 同步；代码/文档内部仍叫
  `quiet_mode`，见 `QUIET_MODE` 相关注释）；
- 说明行精简：蓝牙主页面删除两条通用说明（"点击设备进入详情页…"、
  "连接后音量与 EQ…"）；设备详情页只保留一条睡眠免打扰说明（用户给定文案：
  开启后睡眠定时结束不断电、进低功耗并保持蓝牙连接，避免耳机断连提示音/闪灯）；
  扫描页保留首次配对的**操作引导**；`已保存设备 x/5`、空列表提示、
  "耳机不支持 SBC" 警告都保留（它们是状态/错误提示，不是说明）。

**验证**：debug 构建通过、烧录后开机日志正常；待真机确认
（连接/断开、切 EQ、删除确认时页面不再跳动，返回键行为不变）。
