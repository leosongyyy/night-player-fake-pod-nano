# 实验：用 PPA 把 LVGL 画面顺时针旋转 90°（ESP32-S31）

> 2026-11，S31 移植之后。最初目标是回答"现在能不能通过 LVGL 的方式把界面顺时针
> 旋转 90°"，并先只旋转画面、不动触摸来评估流畅度；**旋转本身验证通过后，
> 已补上触摸跟随 + 左右手校准，并收敛成「显示设置」里的正式选项**（见 §3.1/§3.2）。
> 实现入口：`main/core/ui/lvgl_ppa_rotate.c`，开关
> `CONFIG_UI_DISPLAY_ROTATE_PPA`（默认 **y**，只决定"编译进旋转支持"；
> 实际角度在 设置 → 显示设置 → 屏幕旋转方向 里运行时切换，NVS 默认 **90°**）。
>
> 背景：S3 时代试过旋转，因为没有可用的 2D 加速、只能走 LVGL 的软件旋转，
> 帧率暴跌。S31 有 PPA（Pixel Processing Accelerator，缩放/旋转/镜像 SRM 引擎），
> 隔壁 OtoClock 的 `esp_lvgl_adapter` 也是用 PPA 做屏幕角度变换。

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 能不能转 | **能**。PPA 的 SRM 引擎原生支持 RGB565 的 90° 旋转，`esp_driver_ppa` 在 IDF 6.1 里可用（`CONFIG_SOC_PPA_SUPPORTED=y`） |
| 用 LVGL 的旋转 API？ | **不要**。`lv_display_set_rotation()` 是软件旋转：把旋转塞进每个 draw task 的矩阵变换，和 S3 时代帧率暴跌的是同一条路 |
| 本方案 | LVGL 照旧按 460×460 竖屏渲染，**只在 flush 回调里**把整块绘制缓冲交给 PPA 转 90°，再按旋转后的坐标提交面板 |
| 角度 | 0/90/180/270 都在实现里，**运行时切换**（设置 → 显示设置 → 屏幕旋转方向，立即生效，无需重启），见 §3.1 |
| 触摸 | **跟随旋转**：触摸 read_cb 先按同一角度做逆变换，再按左右手做 29/30 缩放（右撇子锚旋转后左上角、左撇子锚右上角，默认右撇子），见 §3.2 |
| 代价 | 内 RAM/DMA 多一块 ~41KB 旋转输出缓冲；每块绘制缓冲多约 1.1ms 旋转时间 |
| 真机结果（2026-11 用户实测） | **左右滑动 + 列表快速滚动，帧率只降约 20%，可以接受**；静止时仍 60fps 量级 |

## 2. 数据流

LVGL 9 在本项目里是 `LV_DISPLAY_RENDER_MODE_PARTIAL` + 双绘制缓冲
（`lvgl_port.c`，单块 460×46×2B ≈ 41KB）。`lv_refr.c` 把失效区域按
"缓冲能装下的行数"切成若干块，每块渲染成**紧凑矩形**（行宽 = 该块宽度）

```
LVGL 渲染 area(w×h) → px_map（紧凑 RGB565，行宽 w×2）
   │
   ├─ 未旋转（默认路径）：就地 rgb565 swap → esp_lcd_panel_draw_bitmap(原坐标)
   │
   └─ 角度 90/180/270（UI_DISPLAY_ROTATE_PPA）：
        PPA SRM（270° CCW = 顺时针 90°）→ s_tile（h×w 紧凑）
        → rgb565 swap → esp_lcd_panel_draw_bitmap(旋转后坐标)
```

### 2.1 为什么只需要**一块**旋转输出缓冲

`lv_refr.c: draw_buf_flush()` 在调用 flush_cb **之前**会
`wait_for_flushing()`（双缓冲时），也就是"上一块缓冲的 QSPI 传输已经完成"
才会进入本次 flush。所以 flush_cb 执行期间没有任何 DMA 在读 `s_tile`，
单块缓冲安全——内 RAM 紧张，这里不学 LVGL 做双缓冲。
（这也意味着旋转与传输不能流水化；要流水化得再加一块缓冲并自己管理
`flush_ready` 时序，见 §8。）

### 2.2 几何映射（顺时针 0/90/180/270，图像坐标 y 向下）

源像素 `(x, y)` → 目标（屏为方形，W=H=460，图像坐标 y 向下）：

| 顺时针角度 | PPA 角度（自检后的映射） | 目标像素 |
|---|---|---|
| 90° | 270° CCW | `(H-1-y, x)` |
| 180° | 180° | `(W-1-x, H-1-y)` |
| 270° | 90° CCW | `(y, W-1-x)` |

于是源区域 `[x1..x2] × [y1..y2]` 的目标矩形：

```
90°  → [H-1-y2 .. H-1-y1] × [x1 .. x2]      （输出 tile：h×w）
180° → [W-1-x2 .. W-1-x1] × [H-1-y2 .. H-1-y1]（输出 tile：w×h）
270° → [y1 .. y2] × [W-1-x2 .. W-1-x1]      （输出 tile：h×w）
```

90/270 时旋转后 tile 的宽 = 源高 h、高 = 源宽 w，行宽 h×2，正好等于面板窗口宽度
（紧凑行，面板驱动按 `x_end-x_start` 计算长度并追加 X gap=10，与未旋转路径
一致）；180° 时宽高不变。本实验只支持方形屏（460×460），非方形屏初始化时
直接拒绝（否则目标区域会越界）。

### 2.3 字节序

面板要"高字节在前"的 RGB565，现有路径在 flush 里
`lv_draw_sw_rgb565_swap(px_map, ...)`。PPA 的 `byte_swap` 只作用于**输入侧**，
用它只会把小端输入解释成大端、输出仍是小端，达不到目的。所以顺序是
**先 PPA 旋转、再对输出 s_tile 做 swap**，语义与原来逐字节等价。

### 2.4 方向自检（重要）

PPA 的 `ppa_srm_rotation_angle_t` 只写了"逆时针（CCW）"，但"逆时针"是图像
坐标还是数学坐标并无明文；写反了画面就变成逆时针 90°，只有上屏才发现。
`lvgl_ppa_rotate_init()` 因此在启动时用一张 32×32 的已知图案跑一次 PPA，
按 `源(x,y) → 目标(n-1-y,x)` 逐像素比对：

- 270° 通过 → 90° 用 270、270° 用 90（文档约定）；
- 270° 不过、90° 通过 → 打印警告并按相反约定建表（硬件约定与文档相反）；
- 180° 与 270° 再各校验一次（映射表其它项也不能想当然）；
- 任一角度不过 → 打印错误、**整体退回未旋转路径**（不会把花屏固件当成功，
  也不会留下"90° 对、180° 错"的半可用状态）。

### 3.1 运行时切换（0/90/180/270）

角度是**运行时状态**，不是编译期常量：

- NVS 键 `rotation`（u8 索引 = 角度/90，默认 90°），开机由 `lvgl_port_init()`
  读出后交给 `lvgl_ppa_rotate_init()`；
- **设置 → 显示设置 → 屏幕旋转方向**（列表四选一）→ `lvgl_port_set_display_rotation()`：
  先改模块角度，再把 `lv_screen_active()` + `lv_layer_top()` + `lv_layer_sys()`
  全部标脏，下一帧整屏按新方向重画（约一帧完成，**无需重启**）；
- 旋转输出缓冲在开机时**总是**分配（哪怕当前角度是 0），所以切换不会在
  开机末期碎片化的内部 RAM 里再申请 41KB；
- 自检覆盖 90/180/270 三个角度（`rotate_selftest()`），映射表里任一角度
  不过就整体禁用，不会出现"90° 对、180° 错"的半可用状态；
- 切换失败（未编译进旋转支持 / PPA 初始化失败）时保持原角度并打日志。

### 3.2 触摸变换（跟随旋转 + 左右手校准）

`core/ui/lvgl_port.c` 的 `lvgl_touchpad_read_cb()` 是唯一的坐标出口（LVGL
indev 与触摸测试/息屏活动/ClickWheel 订阅者共用），变换顺序固定：

1. **按当前生效角度做逆变换**（面板坐标 → LVGL 逻辑坐标）。画面顺时针转 θ
   后逻辑点 p 显示在面板 R_θ(p)，所以触摸要反过来转 θ：

   | 画面角度 θ | 触摸变换（面板 (x,y) → 逻辑） |
   |---|---|
   | 0° | (x, y) |
   | 90° | (y, H-1-x) |
   | 180° | (W-1-x, H-1-y) |
   | 270° | (W-1-y, x) |

   ⚠ 角度取 `lvgl_ppa_rotate_get_angle()` 的**实际生效值**：PPA 初始化失败时
   画面根本没转，这里也必须按 0 处理，否则触摸会和画面对不上。

2. **29/30 缩放校准**（这块屏的经验值），锚角由「显示设置 → 触屏校准」决定：
   - 右撇子（默认）：以**旋转后的左上角**为原点 → x、y 都向 0 收；
   - 左撇子：以**旋转后的右上角**为原点 → x 向右边收、y 仍从顶部收。

   只有"右撇子 + 不旋转"才与加旋转之前的旧代码逐像素等价——旧代码"恰好"
   能用，正是因为它命中的是"右撇子 + 按未旋转方向握持"这一种假设。

## 5. 真机实测数据（2026-11-14，debug 构建、320MHz、40MHz QSPI）

启动日志（方向自检通过，说明 PPA 的 270°CCW 就是我们要的顺时针）：

```
I (1016) ppa_rotate: PPA 旋转已就绪：当前 90°（顺时针），输出缓冲 42368 B，触摸跟随旋转
I (6641) ppa_rotate: 前 500 次旋转：旋转路径平均 1107 us/次（含 PPA + swap + 提交），等效 15.2 Mpx/s
```

| 项目 | 实测 |
|---|---|
| 单块旋转（平均面积约 1.5~1.8 万 px，460x46 量级） | **1105~1107 µs/块**，等效 **15~16 Mpx/s** |
| 静止/跑马灯（`MEM:` 的 `fps=`） | **60~61 fps**（不掉） |
| 左右滑动 + 列表快速滚动（用户主观测试） | **帧率只降约 20%，可接受** |
| 稳态 DMA | free 31,327 B / 最大连续块 **30,720 B**（≥4KB，SD 读 512B 仍安全） |
| `04-lvgl_port` 前后 DMA | 251,403 → 102,807 B（两块绘制缓冲 84.7KB + 旋转缓冲 42.4KB + PPA 驱动/描述符） |
| 稳态 `MEM: iram=` | 80,335 B（本固件已含 WiFi 组件，不能直接和 `IRAM_OBJECTS_PSRAM_S31.md` 的 167,707 对比） |

### 5.1 为什么实测是 15~16 Mpx/s，而不是 blend 那套的 36 Mpx/s

旋转后的输出**行宽只有 92 字节**（= 绘制缓冲的 46 行 × 2B）：一个 460x46 的
横条转过来是 46x460 的竖条，2D-DMA 每写一行只有 92B，既短又不按 64B 对齐，
突发传输效率远低于 blend 那种 920B 整行。这是"分块刷屏 + 旋转"的固有开销，
不是配置问题（burst 已取最大 128）。

另外 LVGL 的 `draw_buf_flush()` 是"先等上一块传完再调 flush_cb"，所以旋转
**无法**与上一块的 QSPI 传输重叠，每块 1.1ms 直接加在关键路径上；一帧如果是
8~10 块，就是 9~11ms。掉 20% 帧率与这个量级吻合。

## 6. 已知限制

1. **只支持 90° 的整数倍**（PPA 的 SRM 只有 0/90/180/270 四档）；任意角度
   （如 45°）需要缩放+插值，不在本次范围内。
   触摸已跟随旋转（见 §3.2）；左右手的锚角是对这块屏的经验校准——若实测
   某个角度下"内收"方向仍不顺手，只需改 `core/ui/lvgl_port.c` 里锚角那一小段。
2. **旋转与传输无法流水化**：LVGL 在 `draw_buf_flush()` 里先
   `wait_for_flushing()` 再调 flush_cb，旋转必然发生在上一块传完之后，
   单块 1.1ms 直接进关键路径。加第二块 `s_tile` 也没用（flush_cb 本身被
   串行化了）。能压的只有"每块的字节数"和"每块的传输效率"。
3. **旋转输出行宽只有 92B**（见 §5.1）：把绘制缓冲的块高对齐到 32 行
   （输出行宽 64B、正好一个 cache line）有望把 15Mpx/s 拉高；代价是块数
   从 10 块变 15 块（固定开销变多），净收益需要实测。
4. **内 RAM/DMA 多 41KB**：`s_tile` 与单块绘制缓冲同尺寸。若以后 WiFi/BT
   吃紧，优先把 `s_tile` 换到 PSRAM 做实验（PPA 支持外部内存输出，但
   QSPI DMA 能否直接读 PSRAM 需实测）。
5. **PPA 与 blend handler 共用硬件**：`UI_PPA_ACCEL` 的 blend client 与
   旋转 client 会排队，但本项目 blend 命中率本就是 0（见 PPA_ACCEL.md §6.2），
   实际不冲突。
6. 息屏/亮屏：亮屏走 `lv_refr_now` 全屏重刷 → 会走旋转路径；面板
   `esp_lcd_panel_init()` 重发初始化不改坐标，无需特殊处理。

## 7. 为什么不用面板 MADCTL 旋转

CO5300 的 `0x36`（MADCTL）有 MV/MX/MY 位，理论上改扫描方向就能零成本转屏。
但本项目的面板组件明确不支持：`panel_qspi_amoled_swap_xy()` 直接
`ESP_LOGW("swap_xy is not supported")`，`mirror_y` 同样不支持（见
`components/esp_lcd_qspi_amoled/esp_lcd_qspi_amoled.c`）。所以走 PPA 是当前
可行的路径；如果以后换屏/驱动支持 MV 位，那会是比 PPA 更便宜的方案
（零缓冲、零像素搬运）。

## 8. 后续可做

1. **触摸校准的实测再标定**：29/30 与左右手锚角是经验值；换屏/换贴合后，
   或用户觉得边缘仍偏，改 `TOUCH_CAL_NUM/DEN` 与锚角公式即可（见 §3.2）。
2. **旋转 + 传输流水线**：双 `s_tile` + 非阻塞 PPA，用 `flush_ready` 回调
   配对，能省掉每块 ~0.7ms 的串行等待。
3. **小块阈值**：面积 < ~1500px 时 PPA 固定开销占主导，可改 CPU 旋转
   （逐像素写列，2 万像素以内约几十 µs）或直接沿用未旋转路径。
4. **面板 MADCTL 方案**：换支持 MV 位的屏/驱动后重估。
